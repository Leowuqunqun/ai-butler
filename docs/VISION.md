## 一句话

**用微信说人话，遥控你自己的电脑——像使唤一个管家。**

不是"远程桌面"，也不是"命令行转发"。是**用 AI 语义替代操作电脑**：
你说要什么，它自己去点、去找、去改，不用你告诉它点哪儿。

## 最终形态（用户视角的完整体验）

目标用户是**完全不懂技术的人**。所以整个旅程里不能出现：终端、配置文件、API key、端口、路径。

### 1. 装

下载一个安装包，双击。或者复制一行命令粘到终端——但**只有这一种情况需要终端**，且对小白可以给图形安装器。
不需要预装 Node、不需要懂 git。

### 2. 连

安装完弹出**引导页**（本地网页）：

- 显示一个二维码 → 手机微信扫 → 完成
- 只问两个问题：
  - 「我要帮你管哪台电脑？」（默认：当前这台）
  - 「你平时用它做什么？」（用来生成初始人格，可跳过）
- **不问** API key、不问工作目录、不问端口

> 关键：扫码页必须**自动换码**。二维码只活约 90 秒，静态图片必然扫不到——
> 这个坑在 M0 已经踩过并且解决了（`src/qr-page.mjs`）。

### 3. 用

在微信里说人话：

```
「帮我把桌面上那堆图按日期整理进文件夹」
「我昨天写的那个文档发我」
「家里那台电脑上有个叫 xxx 的，找出来发我」     ← 多终端
「下周三下午三点的会，帮我记一下」
```

### 4. 它会问

涉及破坏性的事，先问一句，不是先干了再说：

```
管家：要删 32 个文件（都是 .tmp），确认？
你：  确认
管家：删了。另外我把它们移到了废纸篓，一周内还能捞回来。
```

### 5. 它会长记性

```
「以后简历都放 Documents/简历/」
→ 之后自动记住，不用再说第二遍
```

（你说的时候没带「记住」也没关系：它听出这是长期有用的事，会自己记下，并当场说一声）

### 6. 配置也在微信里做

这是"小白可用"的核心：**没有配置文件**。

```
「帮我改一下工作目录到 项目/2026」
「以后别在半夜给我发消息」
「把操作的确认级别调高一点」
```

## 三个决定形态的岔路

### 岔路 1：多终端怎么连？（最难的一块）

**⚠️ 先分清"谁跟谁要通信"——这两件事完全不同：**

| 链路 | 需要穿透吗 | 为什么 |
| --- | --- | --- |
| **手机 → 电脑** | **不需要** | 手机走微信、电脑长轮询腾讯服务器。**iLink 本身就是那个现成的公共中继** |
| **中枢 → 其他设备** | **需要** | 这才需要一条从持有登录态的机器到其他机器的路径 |

所以"在外面用手机遥控家里的电脑"——**核心场景零网络工作**。
跨网问题只在"中枢要指挥另一台不同网络的设备"时出现。

> 为什么必须"唯一持有登录态"：一个微信号的 bot 只能有一个收信方。
> 两个进程同时长轮询会互相抢消息、游标互相打架。M0 实测过。

**跨网的三条真路（不粉饰）：**

| 方案 | 怎么做 | 小白能做吗 |
| --- | --- | --- |
| **借现成组网**（Tailscale / ZeroTier） | 每台设备装一次、登录，组成虚拟局域网，中枢按虚拟 IP 直连节点 | ✅ 双击装 + 登录，个人用免费额度够 |
| **自建中继** | 用户买台云主机跑中继，节点连它 | ❌ 小白搞不定 |
| **自建 P2P 打洞** | 自己做信令 + 打洞，失败回落中继 | ⚠️ 成功率不满，NAT 恶劣时失败，必须兜底 |

**定案（✅）：做成 `ctx.link` seam**（正是 dsh 的做法——`ctx.shell` 能换 sandbox/local，
`ctx.link` 就换传输实现）。M2 只实现两个：

- `link-lan` —— 同局域网直连（零配置）
- `link-tailscale` —— 跨网：检测到 Tailscale 就直接用，没装就引导装

高级用户可自己写 `link-ssh` / `link-relay`。**我们自己不运营任何服务器**——
这与"用户自备 key、数据不出机器"是同一条原则。

### 岔路 2：模型谁付钱？—— ✅ 已定：用户自备 key

引导页**带他申请、粘贴**，做成傻瓜流程（"点这里申请 → 复制 → 粘到这儿"）。
成本为零、隐私最好、和"数据不出机器"一致。代码层留出"托管通道"的 seam，将来真做产品再开。

### 岔路 3：仓库形态？—— ✅ 已定：monorepo

```
packages/
  channel-wechat/     ← 现在这份，已可用（M0）
  core/               ← ctx.channel / ctx.device / ctx.agent 三个 seam + 会话 + 权限
  hub/                ← 中枢：持有微信登录态、路由、设备注册表
  node/               ← 设备节点：接受中枢指令、在本机执行
  link-lan/ link-tailscale/   ← ctx.link 的两种实现
  installer/          ← 小白安装器（M3）
```

理由：dsh 自己就是这么做的（288 个包 + pnpm workspace + patch 组合），
而目标是"整体参考 dsh 的架构"。而且通道层已经独立可用，正好是第一个包。

## 架构：参考 dsh 的具体映射

dsh 的架构本质是四件事，照搬：

| dsh 的做法 | 我们的对应 |
| --- | --- |
| **一切皆插件**（288 包，每个注册一个 `ctx.*` 服务位） | 通道、agent 后端、设备节点、工具，全做成插件 |
| **patch 文件组合**（`cordis.patch.yml`：`id`/`name`/`config`/`disabled`/`insert`） | 同一套机制：用户的 patch 决定装哪些插件、怎么配 |
| **seam 可替换**（`ctx.shell` 可以是 sandbox 也可以是 local；`ctx.llm` 可以是任何 provider） | `ctx.channel`（微信/飞书/…）、`ctx.device`（本机/SSH/远程节点）、`ctx.agent` |
| **profile 分层**（base patch + 用户 profile patch，互不污染） | 内置默认 + 用户覆盖 |
| **会话/存储/权限也都是插件**（`dsh-session-*`、`dsh-storage-*`、`dsh-authorization`） | 同样拆开；尤其**权限/审批**要产品化成"微信里问一句" |

**这正是当前最大的缺口**：现在的代码是"桥 + 后端"两层硬连接，没有 seam 体系。
要产品化，得先把 `ctx.channel` / `ctx.device` / `ctx.agent` 三个服务位立起来。

## 明确不做

- **多用户 / 多人共用**——定位是"你自己的管家"。做多用户会同时引入身份、隔离、配额、滥用四件事，还和"数据不出你机器"直接冲突
- **托管 SaaS**——同上
- **逆向 hook 微信客户端**——版本一升级就崩，封号风险高
- **通用 GUI 自动化（截图 + 模拟点击）**——慢、脆、会霸占你的屏幕，一个任务能烧几十步还不成。**例外**：定死坐标、单一用途的脚本（比如"发一条微信给某人"）
- **在只有一路通道时就抽象"多通道网关"**——现在是投机。等 M3 真有第二路通道时再抽

## 硬骨头（现在就得想清楚，不能含糊）

1. **"遥控电脑"和"关机"物理冲突。** 电脑关了就是关了。产品上要管理预期：
   "管家在你电脑开着的时候在线"。别做"永远在线"的承诺。

2. **小白 + 本地执行 = 安全。** agent 拿到的是你这台机器的 shell。小白不懂风险，
   而**配置文件不可能是他的防线**。必须有产品化的审批机制——在微信里问一句
   "要执行 rm 吗"，而不是让人去改 `allowFrom`。

3. **个人微信的封号 / 合规风险。** 走 iLink（腾讯自己的通道）风险相对低，
   但产品上要如实说明，不能装作没有。

4. **成本。** 一个"管家"背后是持续的模型调用。谁付钱，决定它是开源工具还是商业产品。
   这个问题的答案会反过来影响架构（要不要做用量控制、要不要做额度）。

5. **多终端的网络穿透。** 见岔路 1。没有免费午餐：要么同局域网，要么一个中继。

6. **语音是意外的好消息。** 微信服务端已经把语音转成文字了（M0 已验证），
   小白天然更爱发语音——这条通道白捡。
