## 一句话结论

**能做，而且和这个项目"我们自己不运营任何服务器"的底线是合拍的。**

飞书的长连接是**你的机器主动连出去**的，官方原文：「只需保证运行环境具备访问公网的能力即可，
**无需提供公网 IP 或域名、无需使用内网穿透工具**」✓官方。也就是说，装了微信那套的人，
不需要再多一台服务器、也不需要域名。

代价是三样，都不致命，但都得认：

1. **必须建"企业自建应用"。** 飞书那个"群自定义 Webhook 机器人"**只能单向发**，官方原文：
   「仅支持单方向群组内推送消息，不支持与用户进行消息交互」「不具有任何数据访问权限」✓官方。
   好消息是门槛不高：可以自己免费建一个团队（建的人就是管理员），而且在**测试企业**里
   权限**免审、立即生效** ✓官方。
2. **要引入依赖**（这是通道层第一次不是"零依赖"）。官方 Node SDK 解包 **≈30 MB** ⚙源码；
   但官方组织下另有一个**为"让 agent / 外部服务接入飞书消息系统"而生**的包 `@larksuite/channel`
   （解包 **1.5 MB**，依赖只有 node-sdk + https-proxy-agent，维护者与官方 SDK 同一批 ByteDance 账号）⚙源码。
3. **事件是"至少一次"，不是"恰好一次"。** 官方原文：「整个业务链路上消息通信目前采取至少发送一次的策略……
   即使成功接收仍会收到重复消息」✓官方，失败后按 **15 秒 / 5 分钟 / 1 小时 / 6 小时重推，最多 4 次** ✓官方。
   所以**幂等只能自己做**，而且收消息事件原文明写：**用 `message_id` 去重，「不要依赖 event_id」** ✓官方。
   这一条走错，表现就是"同一句话被执行两遍" —— 正是 Telegram 通道那句
   **"宁可漏，不可重"**要防的事。

## 一、接入形态：为什么只有"企业自建应用"这一条路

飞书的机器人分两类 ✓官方：

| 形态 | 能收消息吗 | 说明 |
| --- | --- | --- |
| **群自定义机器人**（Webhook） | **不能** ✗ | 原文「仅支持单方向群组内推送消息，不支持与用户进行消息交互」「不具有任何数据访问权限」「不能响应用户 @ 机器人的消息」；发送消息接口也写明它**无法调用** |
| **应用机器人**（自建应用 / 商店应用） | 能 ✓ | 双向收发、读写数据都走这条路 |

单向的那个连"回一句"都做不到，所以**双向只能建自建应用**。

**身份门槛**（✓官方）：官方只要求「必须先成为飞书的企业用户」。测试阶段
「开发者可自行创建一个新企业，在新企业中创建应用、添加权限，实现权限免审」——
也就是说**用手机号免费建一个团队，你就是超管，能自己把整条链路跑通**。△推断：
"任意成员可建应用、但权限生效与上线发布要管理员审"是这个平台的常规设计，官方没有明写这一句。

**免费版调用量**（✓官方，但有个洞）：基础免费版内，单租户所有自建应用的 API 调用量有上限，
文档写的是「2026 年 6 月限时 100 万次/月」，历史基线是 10,000 次/月，超了报 `99991403`。
**好消息：事件订阅（也就是"收消息"）不计入调用量** ✓官方。
?未核实：**2026-10-14** 已经过了文档里那个"2026 年 6 月"（这句是那天写的），当月实际额度要去管理后台的费用中心看。

## 二、事件订阅：长连接 vs HTTP 回调

| | **长连接（WebSocket）** | HTTP 回调 |
| --- | --- | --- |
| 需要公网吗 | **不需要** ✓「无需提供公网 IP 或域名、无需使用内网穿透工具」 | **需要** ✗，且「必须是 IPv4 公网地址」 |
| 加密与验签 | 官方原文：「内置通信加密和鉴权……**无需额外解密、验签逻辑**」✓ | 自理：Encrypt Key（AES-256-CBC）+ Verification Token + `X-Lark-Signature` |
| 谁能用 | **仅企业自建应用**（商店应用不支持）✓ | 都行 |
| 适合本项目吗 | **适合** —— 和微信那条"机器主动连出去"的形状一样 | 不适合（要公网、要自己搞加解密） |

**长连接的硬约束**（✓官方，每一条都会影响设计）：

- 「接收到消息后，需要在 **3 秒内**处理完成且不抛出异常，否则会触发超时重推机制」——
  现有架构**天然满足**：通道收信只 `emitMessage`（非阻塞），干活的是核心层的队列
  （见 `packages/seam-channel/README.md` 的"规则 3"）。但要守住：**SDK 的处理函数里不许 `await` 干活**。
- 「每个应用最多建立 **50 个连接**」—— 够用，但别在调试时狂开进程。
- **集群模式不广播**：多个客户端同时在线时，事件只随机投给**其中一个** ✓官方。
  这条和微信那边"同一账号只能有一个进程在收"是同一类问题 ▶ `butler node` 那道安全闸的同类。
- 长连接是**飞书 SDK 提供的能力**（官方原文说"你可以在本地服务器集成飞书 SDK"），
  协议是 **WebSocket + protobuf 帧** △/⚙ —— 自己从零实现不划算。

**可靠性语义**（✓官方）：

- **至少一次**；失败重推 4 次（15s / 5min / 1h / 6h）；3 秒内不响应（或抛异常）就算失败。
- 去重：事件概述说用 `event_id`，但**收消息文档明确说用 `message_id`、「不要依赖 event_id」** ——
  两处口径不一致，**以收消息文档为准**（这条我们按原文核过，不是推断）。

## 三、鉴权与权限点

**拿 token**（✓官方）：`POST /open-apis/auth/v3/tenant_access_token/internal`，
body 是 `app_id` + `app_secret`，**最大有效期 2 小时**；剩余不足 30 分钟时再调会返回新 token（新旧并存）。
只有"以用户身份操作"才需要 `user_access_token` —— **我们这个场景不需要**，省掉一整套 OAuth。

**scope（权限点）**：名字很容易写错，这里按官方原文抄 ✓官方：

| 要干的事 | scope |
| --- | --- |
| 以应用身份**发消息** | `im:message:send_as_bot`（推荐）／`im:message`／`im:message:send`（历史） |
| 收**单聊**消息 | `im:message.p2p_msg:readonly` |
| 收**群里 @ 机器人**的消息 | `im:message.group_at_msg:readonly` |
| 收**群内全部**消息 | `im:message.group_msg`（**敏感权限**） |
| 上传图片 / 文件 | `im:resource` 或 `im:resource:upload` |
| **下载消息里的资源** | `im:message` / `im:message:readonly` / `im:message.history:readonly` |

⚠️ 最后一行是**最容易踩的坑**：上传用 `im:resource`，**下载不用它**（要 `im:message*`）✓官方。

**权限生效**（✓官方）：分"免审"与"需审核"；**测试企业内全部免审、立即生效**，但**不自动同步到正式版** ——
正式发布要再申请一遍。所以开发能很快跑起来，上线那一步必然要过一次管理员。

## 四、创建与发布流程（以及人会卡在哪）

✓官方六步：① 开发者后台建企业自建应用 → ② 添加「机器人」能力 → ③ 申请上面的 scope →
④ **事件与回调**里选**长连接**、订阅「接收消息 v2.0」→ ⑤ 创建版本并申请线上发布（管理员审）→
⑥ 在客户端搜机器人名，或群里添加。

**最容易卡的三处**（都在"配置态"而不是代码里）：

1. **配置/权限/事件的任何改动都要发新版过审才生效** —— 直接改配置不生效，会让人以为代码没写对。
2. ⚠️ **保存长连接配置时，本地客户端必须已经在线** ✓官方 —— 顺序反了就一直保存失败。
3. **用户必须在应用的"可用范围"内**，否则搜不到机器人。

**"不上商店"不等于"不用审核"** ✓官方：自建应用走的是**本企业管理员**审（商店上架才是飞书平台审）。
管理员可以开免审 —— 你自己建团队的话，那个管理员就是你。

## 五、映射到 `ctx.channel`：要写的 5 个方法 + 三个真问题

新通道的全部契约就是 5 个方法（`start` / `stop` / `sendText` / `sendFile` + 可选 `check`），
附件在通道内部落成本机文件，引用由通道自己决定怎么显示。逐项对到飞书：

| 契约 | 飞书这边怎么做 |
| --- | --- |
| `start()` / `stop()` | `@larksuite/channel` 或 SDK 的 `WSClient`；收尾照现成写法走 `ctx.effect(() => () => this.stop())` |
| `sendText(to, text, opts)` | `POST /open-apis/im/v1/messages?receive_id_type=chat_id`，`msg_type=text`；**content 是转义后的 JSON 字符串**；text ≤150 KB |
| `sendFile(to, path, opts)` | **两段式**：先 `POST /im/v1/images`（≤10 MB）或 `/im/v1/files`（≤30 MB，`file_type` 由后缀映射）换 key，再发 `image`/`file` |
| `opts.quote` | 飞书**有原生引用**：`POST /im/v1/messages/:message_id/reply` —— 通道自己走它，文本一个字不改（和 Telegram 一样）。**接缝不用改** ✓ |
| `opts.contextToken` | `chat_id`（要原生回复时把 `message_id` 一起塞进去）△ |
| `InboundMessage.fromId` | `event.sender.sender_id.open_id`（`ou_` 前缀，**应用内**稳定；跨应用才需要 `union_id`） |
| `InboundMessage.text` | `content` 是**序列化后的 JSON 字符串**，要二次 `JSON.parse`；里面 `@` 变成 `@_user_N`，**得拿 `mentions[]` 换成真人**（群聊必需） |
| `InboundMessage.quote` | 事件只给 `parent_id` / `root_id`（**仅回复场景有值**），**不给原话** —— 要么多调一次取消息内容，要么只说明"在回某条"（△ 见下面决策 3） |
| `InboundMessage.files` | 先下载到本机再交出：`GET /im/v1/messages/:message_id/resources/:file_key?type=image\|file`；>100 MB 要 `Range` 分片（单片 ≤32 MB） |
| `check()` | 自己做是拿一次 `tenant_access_token`（免费）→ 通了报应用名，被拒了给"去开发者后台看一眼"（照 Telegram 那句 `getMe` 的写法）。⚙ **实际怎么做的**：站在官方包上就是一次 `getAppInfo()` —— 免费的一次 REST 调用，`tenant_access_token` 由 SDK 内部自己取（`packages/channel-feishu/src/index.ts` 里那个 `withTimeout(this.lark.getAppInfo(), …)`）。⚠️ 第 69 轮量到原来这里只写了"拿一次 `tenant_access_token`"，读者会以为要自己写这一步 |
| `setTyping` | 飞书没有"正在输入" → 基类默认 no-op，不用管 |

注意这张表里"**谁来做**"的差别很大：如果站在官方 `@larksuite/channel` 上（见下面第六节），
`start` / `stop`、断线重连、去重、媒体上传**都已经有了** —— 这张表大部分是"接线"，不是"实现"。

**三个真问题**（不是"能不能"，是"要想清楚"）：

1. **幂等**：至少一次 + 重推 4 次 ⇒ 必须按 `message_id` 去重，而且**去重表要落盘**
   （长连接没有 Telegram 那种 `offset` 游标可存，进程重启后靠什么判断"这条见过"要设计）。
2. **`@_user_N` 与引用**：群里 @ 机器人时正文里是人名占位符，不换掉的话 agent 看到的是一串乱码；
   引用又只有 ID 没有原话。这两件事决定了"群聊体验是能用还是别扭"。
3. **语音不转写**：飞书能收发语音（`audio`，且**发送必须 OPUS** ⚙），但**不提供转写** ✗ ——
   和 Telegram 是同一个诚实缺口：如实告诉用户"听不懂"，而不是假装收到一句话。

## 六、代价与工作量估算（以 Telegram 那条 1196 行为基准）

| 离线测试 | 可做 | REST 部分照 `channel-telegram/test/fake-telegram.mjs` 那套假服务器；事件映射写成纯函数单测；长连接那层做成薄壳 + 注入假 client |

### 估算 vs 现实（做完之后回填 —— 估算错了要记下来，不然下次还错）

| 项 | 估算 | 实际 |
| --- | --- | --- |
| `packages/channel-feishu` 的 src | 200–400 行 | **901 行 / 6 个文件** —— 低了约一倍 |
| 它的离线测试 | "可做"（未给数） | **1016 行 / 52 个用例**，另加 `packages/cli` 里 4 条端到端 |

**低在哪儿，值得记一笔**：估算把"协议那块被官方包接走了"算得很准（WebSocket / protobuf /
心跳 / 重连，我们一行都没写 ✓），但**没算"能交给用户用"的那一层**：

- **落盘去重**：官方的 `SafetyConfig.dedup` 只在内存里，而飞书是"至少一次"投递 + 重推最远
  6 小时后到 —— 重启就丢，所以 `seen.ts` 得自己写；
- **自检 `check()`**：`doctor` 要能说清"哪一项没配好"，而不是只报"连不上"；
- **失败时的人话**：官方抛英文行话（实测抓到过两句），得翻成"事实 + 出路"；
- **附件落盘**：官方给的是字节，落到哪、叫什么名字、什么权限，是我们的事；
- **探针 `probe/`**：让用户不必碰开发者后台的那条路（扫码注册 + 存凭据）。

教训：再估"站在官方包上"的通道，除了协议，还要把**自检 / 失败文案 / 落盘 / 探针**这四样算进去 ——
它们不在协议里，但少了任何一样，这个通道就交不到用户手上。

还有一处**被现实纠正的估算**：表里说离线测试"照 Telegram 那套假服务器" —— 实际做成了
**假在官方通道的接口上**（`test/fake-lark.mjs`），理由是协议不是我们的代码：该证明的是我们这层
翻译对不对，而不是再实现一遍飞书的服务端。（`test/policy.mjs` 是例外：它**故意用真的官方包**，
钉住"我们传下去的 policy"和"官方接住了什么"一致。）

**"真机验收不可自动化"这一条估对了** —— 到现在它仍是唯一没做的那一格。

**里程碑建议**：M-a 只做"收文本 + 原生引用 + 幂等"（能对话就算通）→ M-b 媒体（图/文件/语音）→
M-c 引导页 / `doctor` / 文档 / GETTING-STARTED。

## 七、开工前必须先定的五件事（**都定了** —— 这是动工前的清单，答案写在这儿）

1. **走 `@larksuite/channel` 还是官方 node-sdk 自己写？** → **`@larksuite/channel`**。
   它的能力清单已经读过：L1 传输（WS 长连接 / 自动重连 / 心跳 / webhook 模式）、事件归一化、
   `SafetyConfig.dedup` 去重、流式卡片、媒体上传、`registerApp` 一键扫码注册，全是现成的；
   许可证 **MIT**（与官方 node-sdk、与本仓库一致）。于是我们自己要写的只剩"它 ↔ `ctx.channel`"
   那一层。**这一条从"倾向"升级为"推荐"**，依据见第六节与第八节。
2. **群聊支持到哪一步？** → **单聊 + 群里 @**（`policy: { requireMention: true }`）。
   常规权限下群聊**必须 @ 机器人才收得到**；想收群内全部消息要申请**敏感权限**
   `im:message.group_msg`，而且改权限要发版过审。所以 M-a 只做单聊 + 群里 @。
3. **引用怎么表现？** → **两个都要了**：回复走原生 reply（飞书自己会把被引那句贴在气泡上），
   **同时**把被引原文取回来压成一行交给内核（`toQuoteLine`）—— 因为接缝要的是"他在回哪句"的
   **文本**，而原生 reply 只有飞书可见。
   ⚠️ 反过来，发出去的消息里**不再**自己顶一行 `↩…`：那会和飞书贴的那句重复（实现里写着这条）。
4. **认主存哪个 ID？** → 官方给的 `senderId`，也就是 **`open_id`（`ou_…`）**。
   这不是猜的：官方类型对 `dmAllowlist` 的说明写明了 —— "entries are **sender ids** matching
   `NormalizedMessage.senderId`: an `open_id` (`ou_…`)"。认主的规矩见第十二节第 5 步。
5. **API 额度谁付？** → **这不是决策，是运维注意**：免费版有月度上限（事件订阅不计入），
   重度使用要去管理后台确认额度。⚙ 今天的实际额度仍属未核实（第九节第 2 条）。

**M-b（入站附件）也做完了**：收到的图片/文件用官方 `downloadResourceToFile` 落进
`<管家>/state/files/feishu/`（文件名是 `<ISO 时间>-<消毒过的原名>`，跟微信那边同一个起法），
再折成接缝要的 `LocalFile`。三条纪律写在实现里：**一个附件失败不拖累整条消息**、
**超过上限的不交给 agent（落了盘也删掉）**、**文件名是对方给的，一律消毒**。
`maxFileMb` 默认 30 —— 而且它在构造函数里兜了一次底：`static Config` 的默认值只有经 cordis
装载才生效，直接 `new` 出来时少了这一行，上限会变成 `NaN`（`size > NaN` 永远为 false），
**限流被静默关掉**。这个洞是离线用例抓到的。

**查证过的两件事（都是读了官方实现，不是猜的）**：

1. **`requireMention` 只管群聊**。官方那道闸门先按 `chatType` 分流（`evaluate()` 里
   `chatType === "group" ? evaluateGroup : evaluateDm`），而
   `if ((cfg.requireMention ?? true) && !msg.mentionedBot) return "no_mention"`
   **只写在 `evaluateGroup` 里** —— 所以**单聊不用 @ 它**。我原先代码注释里那句
   "单聊不受影响"是没验就写下的，现在它被实现证明了（注释也留了出处）。
2. **`dmMode` 默认 `'open'`** —— 实现里是 `dmMode ?? "open"`，而这个默认值**不在类型声明里**
   （`botLoopGuard` 那条明确写了 "Off by default"，它没写，所以只能读实现）。含义：
   **企业里谁都能单聊驱动机器人**。这跟主 README 里"默认第一个发消息的人就是 owner"
   是同一类事，所以记在这儿。想收紧得先把 `dmMode` / `dmAllowlist` 透出来（没做）。

这两条有一个**真·契约测试**钉着：`test/policy.mjs` **故意用真的官方包**（别的用例都假在
接口上），断言"我们传下去的 `policy`"和"官方 `getPolicy()` 接住了什么"一致 ——
官方哪天改了字段名，这里会先红。构造不联网，所以它仍然完全离线。

**同一个洞咬到第三次，所以这次一次修干净。** `static Config` 里的默认值只有**经 cordis 装载**
才生效，而这个类是能被直接 `new` 出来的（测试会那么干）。前两次分别是：`maxFileMb` 少了兜底
变成 `NaN`（`size > NaN` 恒为 false，**限流被静默关掉**）、`allowChats` 少了兜底在构造函数里
`.length` 抛 TypeError（`appId` 同理，`start()` 里的 `.trim()` 会崩）。现在构造函数把**每一个**
带默认值的字段都兜一遍（用 `??`，只替掉"没给"，不覆盖用户显式给的 `0` / `false`），
并且有一条用例专门"只给必填项就构造"钉着它。

这个洞本身是**我自己的测试纪律逼出来的**：那条用例是我用一行脚本手验报错信息时崩出来的
（`node -e` 直接 `new`），而不是被现有用例抓到的 —— 因为现有用例都覆写了 `makeChannel`。
顺带发现 **Telegram 那条通道的 schema 有同样的形状**（`allowFrom` / `maxMediaBytes` 等默认值），
它现在由 cordis 兜着不会出事，但同一类地雷还在那儿 —— 没修，记在这儿。

**"跑起来之后"的稳定性也审了一遍：三层不 await 的异步链，落点各不相同。**
一条消息进来要过三段没人 `await` 的链，任何一段漏出去都会变成 **unhandled rejection** ——
而 Node 默认把它升级成**进程退出**，也就是"某条消息出错，整个管家没了"：

| 那一段 | 原来的样子 | 现在 |
| --- | --- | --- |
| 官方包 → 我们的回调 | `void this.handleIncoming(msg)`，没 catch | 挂 `.catch`，记一条 error |
| 接缝的 `emitMessage` | `try { handler(msg) }` —— **接得住同步，接不住 async** | 消费者只有内核那一个，由内核自己兜（下一行） |
| 内核的 `onInbound` | `void this.onMessage(msg)`，没 catch | 挂 `.catch`，记一条、丢掉这条 |

内核那条要分清：agent **干活**那条路**本来就有**保护（`loop()` 里 `try/catch`，还会回用户
一句"我这边出错了：…"）—— 没有落点的只是 `onMessage` **入队**那一步（认主、写状态文件
都可能在这一步失败）。这条修在用**真路径**（`channel.emitMessage` → 接缝 → 内核 wrapper）
跑的核心层用例上钉着，而且**证伪过**：把那行改回去，用例立刻失败。

顺带修掉一个更实在的：**去重表写不进去时，整条消息会被吞掉**。
`SeenStore.save()` 失败是往外抛的，一路穿到 `handleIncoming` —— 于是"家目录只读 / 磁盘满 /
`state` 被占成了一个文件"的机器上，用户发了消息**毫无反应**。现在落盘失败只叫一声（记 warn），
内存里那张表照样管事：**跨重启那层保护暂时没了，但消息照送**。取舍写在 `seen.ts` 里 ——
去重是保护，投递才是本职，宁可漏一次去重，也不能把消息吞了。

**最要紧的一条：真机第一枪之前的状态，我原来根本走不到。**
`doctor` 在一个空的飞书配置上不报"还没填凭据"，而是说**"配置里一行都没有"**、
`1 个插件没装上来`；`butler run` 更直接 —— 起不来。因为我在**构造函数**里就把官方通道
造了出来，而官方包在**构造时**就校验凭据（实测抓到的原话）：

    [error]: [ 'appId is needed' ]
        ✗  channel  @butler/channel-feishu

插件是**装载时**构造的，于是"还没填凭据"——这个**最该看到友好提示**的状态——变成了
插件装载失败，而 `check()` 和 `start()` 里那两段人话**永远到不了**。凭据是 `butler run`
从 `state/secrets.json` 注入的，所以"还没填"是一个**正常状态**，不是错误状态。

修法：官方通道**懒造**（第一次真要用才造），"没凭据"于是降级成"插件装得上，但自检里
报 ✗、启动时说一句人话"。修完之后同一个空配置：

    ✓  channel  @butler/channel-feishu
    ✗  飞书登录态    还没有填 app_id / app_secret
        → 先跑 `bash packages/channel-feishu/probe/run.sh --save`（扫码最省事，会把凭据装好）；…

**为什么 41 个用例全没抓到（同一类盲区第三次）。** 崩的那行在构造函数里，而测试用的
`makeFeishu` 覆写了 `makeChannel` → 官方通道从来没被**真**造过；唯一碰真官方包的
`test/policy.mjs` 又总是带着假凭据。现在有一条用例专门用**真类 + 空凭据**构造，
它就是这条 bug 的判据。

顺带修掉**同一个谎**：`check()` 的 fix 和 `start()` 的报错原来都写着"跑 `butler run`
选飞书，它会开二维码给你扫" —— **不会**。实测 `butler run --im feishu`（没凭据）起的是
一个**本地粘贴页面**（`飞书应用的 app_id：还没有，起了一个本地页面让你贴 http://127.0.0.1:…`），
会开二维码的是**探针**。两处文案都改成指向探针了 —— 一个不会发生的事写进 fix 里，
比不写更坏：用户会照着做，然后卡在那儿。

顺手验了 **Telegram 是同一个形状**（空 token 直接 `new` 就抛）：它现在由 cordis 兜着
不会出事，但凭据没填时同样会**装载失败**。没修，记在这儿。

**把"出错"这条路也跑了一遍（假凭据，真连一次官方长连接）。** 真机上最容易撞上的不是成功
路径，而是"凭据填了但不对"。三处的实际表现：

| 在哪 | 你看到什么 | 评价 |
| --- | --- | --- |
| `doctor` | `拿应用信息没成功：（没有 code） failed to get tenant_access_token, code: 10003, msg: invalid param` + 两种可能 | 好：说事实、不说教、不泄露凭据 |
| `butler run`（凭据没填） | 起一个本地粘贴页面（见上一段） | 好 |
| `butler run`（凭据不对） | 原来只有一句英文行话 `could not resolve bot identity…`，**不说怎么办** | 已修：包一层中文事实 + 出路 + 官方 code，原文一个字不改 |

顺带**证明了接缝是对的**：探针 `--save` 写的 `{version, channels:{feishu:{appId,appSecret}}}`
和 CLI 读的**完全一致**。（这一步我一开始还怀疑过 —— 因为我自己手写的测试文件形状写错了，
`doctor` 说"还没有填"，那其实是对的。）

新加的那条用例除了断言"要说怎么办"，还断言**那条一次性授权链接不出现在消息里**
（`context.consoleUrl` 是签了名的一次性凭据，官方类型里写明绝不可回显）—— 自检那条路原来
就有这个断言，现在连接失败这条路也有。

**探针终于有测试了（8 条）。** 它是整个流程的第一步，却是唯一没人守的入口。为了能测，
把"凭据落到哪、怎么落"抽成了 `probe/save.mjs`（探针依旧**不 import 适配层**，只用官方包 +
这个只写文件的小模块）。测的是：形状、0600、**合并写**（不碰别人的 token）、坏文件覆盖、
不留临时文件，以及 `--dry` **不联网、一个文件都不写**。

其中"形状"这条兼职**跨包契约** —— 这是这轮真正的收获：探针写下去的形状和 CLI 读的形状，
原来是**靠人眼对**的（两边各自的测试都绿，合起来不通的话谁也不知道）。现在写的那半在
`test/probe.mjs` 钉着，读的那半在 `packages/cli/test/secrets.mjs` 钉着，改任何一边另一边会红。

**但"两半各自钉住"还不等于"合起来通"。** 所以又加了一条**真的跑一次**的集成测试
（`packages/cli/test/probe-contract.mjs`）：拿假凭据**真的把探针跑起来写一遍**，再用
CLI 自己的读法读回来、并走一遍 `butler run` 的注入那一步。它不断言退出码 ——
连不上飞书是意料之中的（这一步验的是"存下来"，不是"连上"）。

顺带钉住一个**用户能感觉到**的性质：**凭据写盘发生在连长连接之前**。所以"新应用权限还没配齐、
第一次连不上"时，**凭据已经存好了** —— 修完权限直接 `butler run`，不用重扫。

顺手修掉 dry 里的一个小谎：`--dry --save` 原来固定打印 `~/.butler/...`，而你用 `--home=`
时它说的就是个**错地方** —— 偏偏"存到另一个管家目录"是这条路上最常见的坑。现在说真路径。

**"两半都对"之外，还有四条真的端到端**（`packages/cli/test/m1-feishu-e2e.mjs`）：真
`FeishuChannel`（官方包换成假实现 —— 协议不是我们的代码）+ 真 `ButlerCore`（真队列、真会话、
真去重）+ 假大脑。它们钉住验收标准里 M-a / M-b 那几句：一条来信走到大脑、回话走**原生引用**回
那条来信、同一条 `messageId` 重推只算一次、**换个内核 + 同一个管家目录**重推仍然不算数（跨重启
去重）、一张图交到大脑手上时已经是本机可读、内容对得上的文件。

反验了**两种不同的坏法**（这一步比测试本身更值钱）：去掉去重（`has()` 恒假）→ 去重那条红；
让去重表**不落盘** → **只有跨重启那条**红、进程内那条仍绿 —— 正好说明跨重启那条量的是"落盘"
这一层，而不是别的东西在替它挡着。

顺带在产品级补了一条回归（`packages/cli/test/real-composition.mjs`）：`boot()` + 包名寻址 +
**空凭据**的飞书那一行必须装得上 —— 第 8 轮那个 bug 用户看到的就是"装载失败"。
（反验：把构造时的急切校验放回去，它立刻红。）

**已经接进 CLI 了**（这条原来列在上面，做完了）：

- `butler init --im feishu` / `butler run --im feishu` 都认
- 一个包要**两项**凭据（`app_id` + `app_secret`）—— 原来的结构是"一个包一项"，
  所以扩成了数组：引导页挨个问，**已经存过的那项不重问**，配置里手写过的那项一个字不动
- 探针加了 `--save`：扫码之后把两个值**按 CLI 认的格式**写进 `<管家>/state/secrets.json`
  （合并写、0600、原子写、不打印凭据）—— 于是"扫码 → `butler run`"是一条完整路，
  用户不用手抄任何一串东西。默认写 `~/.butler`；用 `--config` 把家安在别处时加 `--home=`

### 第 14 轮：一条"照着敲也敲不出来"的提示（发行版用户）

`install.sh` 是**从 tarball 装**进 `~/.butler/prefix` 的，**不克隆源码** —— 可四处的提示
（适配层的 `missingCreds`、连不上时的 `connectFailed`、CLI 的凭据 hint、引导页）全都在让你跑
`bash packages/channel-feishu/probe/run.sh --save`。装了发行版的人照着敲只会得到
`No such file`：**一条用户照着做也做不到的提示，比没有提示更坏。**

改法不是"再多写一条命令"，而是让提示**按这个包自己的位置算**（`src/probe-path.ts`）：
源码树里算出带绝对路径的 `node …/probe/smoke.mjs --save`，装完之后算出包内路径 ——
**同一个式子，两种装法都对**；而且**先确认文件真的在**，不在就不提探针这条路（退到开发者后台那条）。

顺带两件小事，都是"不然迟早会烂"的那种：

- `package.json` 的 `files` 里加上 `probe` —— 否则装完之后探针不在，上面那个式子永远算出 null。
  这条**有测试盯着**：把 `probe` 从 `files` 里去掉，测试立刻红。
- 那句话只有**一份文本**（`scanHint()`），两个包共用 —— 同一句让用户照着敲的话抄两遍，
  就迟早有一遍过期。

### 第 15 轮：第一枪最容易查错方向的三件事

1. **两条长连接会分流投递。** 探针验通了没关，又起了 `butler run` —— 同一个应用两条长连接时，
   飞书把事件**分流**给其中一条：表现是"消息偶尔不回"，而两边看起来都正常，最容易往错的方向查。
   文档里本来就写着，但用户在终端里盯的是探针 —— 所以现在**探针自己在连上之前说这句**
   （`--dry` 的说明里也有）。而且只留**一份文本**（同一个函数两处调）：两处各写一遍，
   就迟早有一遍过期 —— 这条教训第 14 轮刚吃过。测试盯着这句话（把函数清空，它立刻红）。
2. **`--save` 之后连不上 ≠ 白跑。** 存盘在连接之前，凭据已经留住了；以前失败信息没提这茬，
   用户会以为白扫了一次、又去重扫 —— 而重扫解决不了那三类原因（应用没配长连接 / 缺权限 /
   改完没发版）。现在失败信息会把这句话说出来。
   ⚠️ 只在**真的存过**之后才说（`saved` 标志，不是看 `--save`）：扫码注册自己失败时什么都还没写,
   那时说"已经存好了"就是撒谎。
3. **第一条消息必须你自己发。** 内核的认主不是配置项，而是**第一条来信**：默认没认主时谁先说话
   谁就是这台机器的主人（之后能遥控它跑命令），别人发消息它会**一声不吭**
   （日志里只有 `忽略不属于主人的来信 from=…`）。而飞书 `dmMode` 默认是 `open` ——
   **同一个企业里谁都能单聊这个机器人**。手册现在把这条写成第 5 步，并给了"想彻底钉死"的做法：
   用探针打印的 `senderId` 写进 `<管家目录>/state/state.json` 的 `owner`。
   ⚠️ **第 34 轮纠正**：当初这句是**空话** —— 那时候生成出来的配置里根本没有 `stateFile`，
   `SessionStore` 是纯内存，`state/state.json` **压根不存在**，写进去没人读。见下面第 34 轮。

### 第 16 轮：把"中间那道缝"补上 —— 凭据真的进到插件身上了吗

到这轮为止，凭据这件事**两头都有测试**：契约那头（探针写出来的形状 == CLI 认的形状，
`packages/cli/test/probe-contract.mjs`）和作用那头（给 `injectChannelSecrets` 一组 rows 和文件，
它填得对，`packages/cli/test/secrets.mjs`）。但**没有任何一条**证明"用户在探针里存好凭据之后，
`butler run` 装出来的那个飞书插件身上真的有这两串" —— 而那正是用户会问的那句话：
**"我明明扫过了，它怎么说没填？"**

现在有一条走**真实三步**的测试（`packages/cli/test/secrets.mjs`）：`loadConfig`（读）→
`injectChannelSecrets`（填）→ `boot({ rows })`（装），断言 `ctx.channel.config.appId / appSecret`
就是存进去的那两串 —— 落在**插件实例**上，不是只改了个本地副本。（`boot` 的 `rows` 是
"调用方给的行优先"，本来就是为这一步留的口子。）全程不联网：飞书那行的构造是懒的。

反验用的是**漂移型**故障：把飞书那一项的 `key: 'appId'` 改成一个字母的 `'appID'` —— 凭据就填不进去，
测试立刻红。这类错（拼错一个字母）恰恰是这种"隔着三层"的配置最容易出的。

### 第 18 轮：查"官方给的东西我们会不会弄丢" —— 抓到一个会让消息消失的 bug

这轮没加功能，而是去**读官方实现**（它打包成一个 `.mjs`，切字符串读的），把"站在官方包上"
这句话落到实处：官方导出的 `normalize()` 会把飞书**每种消息类型**渲染成人能读的文本 ——
`text` 原文、`post` 拍平成 markdown 风、`interactive` 把卡片里的字抠出来、`merge_forward`
展开整段聊天记录、`share_chat`/`share_user` → `<group_card id="…"/>` / `<contact_card id="…"/>`、
`location` → `<location name="…" coords="…"/>`、`system` → 渲染过的模板……共 **17 种**。

**然后发现我们这层只让 `text` / `post` 带正文。** 于是那些**只有文本、没有附件**的类型
（合并转发的聊天记录、卡片、群名片、联系人、位置、系统消息……）会被**整条丢掉**：
用户看得见自己发了东西，大脑收到的却是一个**空提示词**（内核那条路是
`route.text = msg.text ?? ''` → `promptFor('')`）。

规则改成按**载体**分，而不是按类型列白名单：

- **附件承载的类型**（`image` / `file` / `audio` / `video` / `media` / `sticker`）→ 正文留空，
  信息走 `resources` 落盘 + 附件提示（M-b 的行为一点没变）；
- **其余类型** → 官方渲染出来的正文就是这条消息**唯一的载体**，必须原样带上。连它给的占位
  （`[unsupported message]`、`<forwarded_messages/>`）也带上 —— 那是它自己的契约
  （"这条我读不出内容"），比**什么都不给**好：至少大脑能如实说"这条我读不了"，而不是对着一条
  空消息编。

证据是 `packages/channel-feishu/test/types.mjs`：**用真的 `@larksuite/channel`** 跑 14 组原始事件
→ `normalize()` → 我们这层，断言"官方给了内容，我们就不能给空"（附件那几种反过来断言
`text` 留空、资源在）。反验是把规则退回旧白名单 —— 量这件事的两条立刻红，而 `post` 那条
依然绿：这说明它量的正是**差异**，不是别的。

### 第 19 轮：查"话题群里的回复会落到哪儿" —— 结论是我们本来就对，但把证据钉住了

上一轮是"读官方实现 → 找到 bug"，这一轮同一个办法得到的答案是**没有 bug** —— 那也得说清楚，
而且要把"为什么对"钉成回归，不然下次谁动一下就可能踩坏：

- 我们的 `reply()` 传的是 `{ chatId, messageId, threadId }`（`sendText` / `sendFile` 两处）。
  官方的签名正是 `reply(msg: Pick<NormalizedMessage, 'chatId' | 'messageId' | 'threadId'>, …)`
  —— **在合同里**，不是我们自己塞的字段；
- 官方不会替我们找会话：`reply(msg, input, opts)` 里写着
  `replyInThread: opts?.replyInThread ?? Boolean(msg.threadId)` ——
  **target 上带 `threadId` 就会 `reply_in_thread`，不带就不会**。
  所以话题里的回复落回同一个话题，普通群里也不会凭空开出一朵话题。

于是这轮只做两件小事：

1. `test/policy.mjs` 开头那份"查过官方实现、写在这里免得下次再查"的清单加了第 3 条（上面那句推导）；
2. `test/plugin.mjs` 加一条只钉**正向**的用例（反向早就被那句
   `deepEqual(fake.replies[0].target, {…})` 钉住了：我们是用 `...(ctx.threadId ? … : {})` 省键的，
   凭空加键它就会红）。反验**只改 `sendFile` 那一处**调用 —— 测试正好红在
   "`sendFile` 那条路也要带"这句上：两处调用各自都有牙，不是一条断言顺带过的。

顺手修掉 README"没验的"里两处**低估自己**的过期话：入站附件下载（M-b 早就接了，代码在
`src/files.ts` + `index.ts`）和话题群的 `threadId`（代码这侧已确定，没验的只是"真飞书的话题群
到底给不给 `thread_id`"）。

### 第 20 轮：查"发不出去的时候，用户听到什么" —— 通道这层补上了退回发送

顺着"读官方实现 ↔ 对照我们这层"往下问了一个更朴素的问题：**发送失败时，用户听到的是什么？**

查到的两半事实：

- **我们这层**：`sendText` / `sendFile` 里那句 `reply` **没有任何兜底** —— 而官方的 `reply` 是会
  失败的（被引的那句被删了 / 太旧了 / 话题对不上）。答案是**刚算出来的**（可能花了几十秒）。
- **内核那层**：`handle()` 是 `try { … } finally { … }`，**没有 catch**。所以答复发送失败时，
  异常一路抛出去，用户**什么都收不到**；而入站去重**已经记过账**，飞书重推也不会再试。
  （对比之下**附件**那条路是有兜底的：`sendFile` 会回一句"附件发送失败：…"。主线答复反而没有。）

这一轮改的是**通道这一层**（"把答案送到"是它的责任）：

```ts
private async replyOrSend(ctx, input, what) {
  if (!ctx.messageId) return this.lark.send(ctx.chatId, input);
  try { return await this.lark.reply({ chatId, messageId, threadId? }, input); }
  catch (error) { this.ctx.logger?.warn(…); return await this.lark.send(ctx.chatId, input); }
}
```

发文本 / 发文件**共用这一个地方**（抄两遍，就迟早有一遍忘了兜底）。取舍和"取不到被引原文时"
那条老规矩一致：**少一段引用，好过什么都不回**；两条路都失败才往上抛。

（顺带记一个踩过的坑：**两边各有一个 `SendResult`，同名不同形** —— 接缝的是
`{ chunks?, fileName?, size? }`，官方的是 `{ messageId, chunkIds? }`。这个文件两个都用，
所以官方那个得改名导入，不然返回类型会悄悄指向接缝那个，然后 `chunkIds` 一片报错。）

反验做了两次、**两种不同的坏法**：① 把退回改成直接重抛 → 两条用例都红（第二条红在"根本没去
尝试发送"上）；② 退回照做、但把最终失败**吞掉** → 只有"两条路都失败才往上抛"那条红。
两次都先确认变异在位（打印改过的那一行 + build 成功）。

⚠️ **内核那半没动**（不在这个目标的范围内，而且它是所有通道共用的）：`handle()` 缺一个 catch
意味着"两条路都失败"时用户仍然听不到任何话。这条记在这儿，该在内核自己的改动里带着测试做。

> **第 21 轮补正**：上面这句把洞说大了。`core` 在**订阅边界**上其实有兜底
> （`void this.onMessage(msg).catch(…)`，注释写明漏出去会变成 unhandled rejection、
> Node 默认把它升级成进程退出）—— 所以**进程不会被弄死**；agent 干活那条路还另有保护
> （`loop()` 里 try/catch，会回一句"我这边出错了"）。会沉默的只剩"发送两条路都失败"和
> "入队那一步出错"这两种。详见第 21 轮。

### 第 21 轮：补上"引导页"那半的测试 —— 顺手抓到一个 Ctrl-C 之后会"卡住"的 bug

目标里点名了「接入 CLI（`ImName`/`secrets`/**引导页**）」，而引导页那条路只被 telegram 用例
盯过。飞书是**唯一要两项**凭据的通道（`app_id` + `app_secret`）—— "两项只填进去一项"正是
这里最容易出的错，所以这轮去补。

**先纠正上一轮的一条笔记**（不能把洞说大）：上一轮写"`handle()` 没有 catch，所以用户什么都
收不到"。查清了：`core` 在**订阅的边界**上就有兜底 —— `void this.onMessage(msg).catch(…)`，
注释还写明"漏出去会变成 unhandled rejection，Node 默认把它升级成进程退出"。所以**不会**把
管家弄死；而且 **agent 干活**那条路另有保护（`loop()` 里 try/catch，会回一句"我这边出错了"）。
真正会沉默的只剩很窄的一种：**发送两条路都失败**，或者**入队那一步**（认主、写状态）出错。
第 20 轮的笔记据此改准了。

补测试过程中的两个发现：

1. **飞书页面的校验是真校验**：点保存到"存好了"之间实测 **~2.5 秒** —— 那是一次真 API
   往返（编的 `app_id` 当然会失败，页面会给出"我知道，就要存这一把"那条出口；`force`
   只改**结论**，不省掉这次校验）。所以**离线用例驱动不了两页整条流程**。
   测试因此分两半：数据那半（两个 `need` + `injectChannelSecrets` **两项都填**）全离线；
   页面那半只 GET 首页、断言那条命令能照着跑。
2. **一个真 bug（已修）**：`signal` 早就接上了，但 `addEventListener('abort')` 对**已经中断过**
   的信号**不会再响**（事件早发生完了）。于是 Ctrl-C 之后：第一项被中断 → 守门循环走到
   **第二项** → 又等满一个 timeout。飞书正好两项，所以最明显 —— **实测 4.2 秒**，在终端里
   看着就是"卡住了"。修法是两处 guard：`ensureChannelToken` 里先查 `signal.aborted`、
   `ensureChannelSecrets` 的循环里中断后不再问下一项。

   证据：修完那条用例从 **4022ms → 16ms**；中断那条 `3003ms → 5ms`。
   反验：把两处 guard 撤掉 → 中断那条立刻红在"实际等了 3003ms"。

（另记一条：§十一 里每一轮的用例数是**当时**的快照，不随后续改动同步；要看当前数字看
README / `docs/EVIDENCE.md`。）

### 第 22 轮：验"装好之后还跑不跑得动" —— 打包产物里那份探针

第 21 轮那个透镜再用一次：**目标点名的路，只被别的形态测过**。文档和引导页都让用户跑
`node <…>/probe/smoke.mjs --save`（`probe-path.ts` 按**包自己的位置**算出来的绝对路径）。
源码树里当然跑得通 —— 可**装好之后**（`install.sh` → `~/.butler/prefix`，那里没有 `packages/`
源码树）呢？这一条以前**只有一句承诺**，没有任何东西盯着它。

### 第 23 轮：让"第一枪"打得响 —— `init --im feishu` 在已有配置上**什么都不改**

前面二十几轮都在补离线证据，而目标的第一句（真机）一直卡着 —— **用户下一步要做的事**才是关键。
于是把手册上的每一步照着做了一遍，结果第一步就断了。

用户手上那台是**住着的房子**（`~/.butler/config.json` 里已经有微信那行、能正常跑）。手册让他
探针 `--save` 存好凭据，然后 `butler run`。可**通道那行没人管**：

- `--im` 只在**新写**一份配置时起作用。已有配置时 `topUpRows` 只补**能力行**，通道行一个字节都不动
  ⇒ 用户为飞书敲了 `--im feishu`、凭据也存好了，配置里那行还是微信。他照着手册走到最后，跑起来的
  **还是微信**，在飞书里发消息**什么都不会发生**。
- 同一类还有两处小的：手册里真写着 `butler run --im feishu`（`--im` 是 `init` 的选项，`run` 没有）；
  `--help` 里写的是 `--im wechat|telegram` —— 而 `IM_NAMES` 里**早就有 feishu**，只有帮助文本是旧的。

修法三处，都不动别人：

1. `topUpRows` 加"通道行**原位换**"：`init --im X`，且认得出是我们生成的配置（有内核行、不是被遥控
   那台）时，把 `id === 'channel'` 那行换成 X —— **位置不动、别的行一个字不动**；包名认不出来就
   **不猜**（可能是他自己接的别的通道）。
2. `initButlerHome` 里 `--im` 没给 = **沿用配置里原来那个**（以前直接默认回微信，等于把用户刚配好的
   飞书悄悄废掉）。`InitResult` 因此带上 `im`，`cli.ts` 的引导文案按它走 —— 不然不带 `--im` 时会打印
   微信那段。
3. 帮助与手册：`--help` 列全三个；手册补上**"中间那步不能省"**（`butler init --im feishu` → `butler run`）。

反验（三处，每次都确认变异在位 + 重新编译）：

| 变异 | 谁变红 |
| --- | --- |
| 不带 `--im` 时默认回微信 | ★★「重跑 init 不许把通道换回去」 |
| 去掉"原位换"那一支 | ★★「住着的房子也能换」 |
| 帮助里拿掉 feishu | 「`--help` 要把每个 IM 都列出来」 |

三条新用例都在 `packages/cli/test/switch-im.mjs`。那个文件里原来那条标题写着"换一个 IM"，
但它用的是 `tempHome()`（**空房子**），测的其实是"第一次就用某个 IM" —— **真·切换**没人测。
另加一条安全性质：认不出来的配置（没有内核行）**一个字节都不动**。

### 第 24 轮：让探针自己说"连上了却没动静"往哪查

接着上一轮的走法（照着手册一步步走）往下走：`init` 修好之后，下一步是 `butler run` 真把飞书拉起来。
先核了两件事，都**没有洞**：

- seam 的 abstract 正好**五个**（`id` / `start` / `stop` / `sendText` / `sendFile`），`check` 是可选、
  `setTyping` 是基础类的静默空实现（"不支持就静默返回"）—— 飞书一个都不缺。
- `real-composition.mjs` 里**已经有**飞书那两格：「没填凭据也装得上、如实报 ✗ 并指向探针」、
  「引导页里那条命令能照着敲」。

真正的洞在最可能出问题的地方，而它**文档里有、探针里没有**：第十二节那张表第 3 行
「连上了，但发消息**毫无反应**」→ 订阅方式不是长连接 / 没订「接收消息」/ 权限改完没发版。
可文档自己的注释早就写着：**"用户在终端里盯的是探针，不是文档"**（第 15 轮为"两条长连接"
加警告时就是这么定的）。于是照同一个模式补了第二份共享文本 `warnEventSubscription()`：
`--dry` 里说一遍、`connect()` 之后再说一遍 —— **一份文本、两处调用**，不漂移。

内容只写**能照着查的锚点**，不替飞书打保票：症状（连上了却一条都收不到）+ 三条最常踩的
（订阅走长连接 / 订上「接收消息」`im.message.receive_v1` / **权限改完必须发版才生效**）
+ 指回第十二节那张表 + 老实说"扫码默认带哪些权限，官方只写到创建 / 授权，我们没在真企业里验过"。

反验：把 `--dry` 里那句调用删掉（并确认变异在位）→ 新用例红在"先把症状说出来"。

### 第 25 轮：`ERR_MODULE_NOT_FOUND` 要说成"这个包没装"，不是一句英文行话

接着上一轮的走法往下走，这次看**用户那台机器上的形态**（不是源码树）。他装的是 `install.sh` →
`~/.butler/prefix`，而手册让装好的机器跑 `node <包内路径>/probe/smoke.mjs --save`。

核了两件，都**没有洞**：打包脚本是 `for d in packages/*/`（**全带上**，不是硬编码清单），
`real-composition` 那两格也早就在。真正的洞在**装的版本**上：

- 用户那台的 `prefix/app` 是**十月**装的 —— 那时还没有飞书通道，`prefix/app/node_modules` 里
  **没有** `channel-feishu`。⇒ 探针文件根本不在那儿；就算跳过探针，`init --im feishu` 写进配置那行，
  `butler run` 时那个包也**装不上**。
- 而装不上时，两条路（`run` / `doctor`）其实**都拦住了**、也**都说了是哪一行** —— 机制是好的。
  但给出的出路是"**修好再启动**"：面对 `Cannot find package '@butler/channel-feishu'`，
  用户只会去翻配置，不会想到"我这台装的版本里压根没有这个包"。

改法：`resolve.ts` 里把 `ERR_MODULE_NOT_FOUND` 单独认出来（Node 给的 `code`），补上
"这个包**不在这台机器已安装的依赖里** —— 最常见的是"升级后新加了通道/能力，还没重装""，
并给出路：**重跑一遍安装那条命令**（README 开头那条 `curl … | sh`），源码树里则
`pnpm install && pnpm build`。**别的装不上原因不接这句**（语法错也叫人重装，就是把人带偏）——
测试两面都钉住了：该说的说 ✓、不该说的不说 ✓。

§十二 也加了**第 0 步**：先确认这台的版本里有飞书这个包（`butler doctor` 里 channel 那行是不是
`@butler/channel-feishu`），没有就先重装/升级 —— 这一步以前**完全没人提**。

反验：把 `notInstalled` 那句判断去掉（并确认变异在位）→ 两条断言各自变红。

### 第 26 轮：发一个**带飞书**的版本 —— 不然"重装一遍"只是把人送回原地

第 25 轮把"重跑安装命令就能升级"写进了手册**和** CLI 的错误信息里。这轮去核实这句话，发现它
**今天是假的**：

  ⇒ v0.1.0 的 tag 里**没有**这个包，`releases/latest/download/install.sh` 取回来的还是那份旧的。

顺带核清两件机制上的事（都没问题）：打包脚本是 `for d in packages/*/`（**全带上** ✓，我发的这个包里

这轮的产物是**发布**而不是代码，所以没有新用例（全仓仍是 937）。发布本身可验证：把 release 上的

### 第 27 轮：升级演练 —— 在**真的装着老版本的机器**上验一遍（脚本留在 `scripts/verify-upgrade.sh`）

第 26 轮把 v0.2.0 发出去了，于是用户下一件真会敲的事就是那条升级命令。可"包里有飞书"（上一轮
验的）和"**在他那台已经装好的机器上升级成功、而且不弄坏他的东西**"是两件事。这轮把后者也跑成
了一个可重跑的脚本：

`sh scripts/verify-upgrade.sh` —— 全程在**临时 HOME** 里（`install.sh` 的 `HOME_DIR="${HOME}"`、
`BUTLER_DIR="${HOME_DIR}/.butler"`，所以把 HOME 指走就整间房子都是临时的），真 `~/.butler` 不碰：

1. 装**真**的 v0.1.0（从 release 下载，那时候没有飞书）；
2. 让这间房子像用户那台：用**老版本的 CLI** 生成配置，再塞一个"用户自己改过"的标记 + 一份
   `secrets.json`（0600）；
3. 用**发布出来的**新 `install.sh` 就地升级（就是 `curl … | sh` 那条）；
4. 验：飞书包 + 探针来了 ✓；`config.json` / `secrets.json` / 0600 **一个字节没变** ✓；
5. 验升级后的语义：`butler init`（不带 `--im`）补能力行但**不换**收信那行 ✓；
   `init --im feishu` 只换那一行 ✓；换完 doctor 里**真的装载成功** ✓；探针 `--dry` 能跑 ✓。

跑通的过程里我自己的断言错了两次，都值得记下来：

- **凭印象猜包名**：我写了 `@butler/channel-wechat` —— 微信那条通道的包名其实是

  所以那条现在失败时会把目录列出来。

  正确行为（它还说了"改完再跑一次 doctor"）。夹具里我一开始只写了一行配置，于是 doctor 如实报
  "少了 agent、core" —— 脚本却把它当成了失败。现在不看退出码，只看它说了什么。

（不改真机器的一个附带好处：这轮把"用户的房子"里会有什么（`config.json`、`state/secrets.json`、
`dsh.patch.yml`）也都看清楚了。）

### 第 28 轮：`butler run` 的门顺序 —— 通道凭据在模型 key **之前**

读 `run` 的实现发现一个对"第一枪"很关键的顺序：`ensureChannelSecrets`（通道凭据）在 `boot` **之前**、
`ensureModelKey`（模型 key）在 `boot` **之后** —— 因为**插件的 config 是构造时读进去的**，通道凭据
必须先进配置行。所以用户 `init --im feishu` 之后第一次 `butler run`，端上来的**第一页就是飞书那页**
（问 app_id / app_secret），既不是微信二维码、也不是模型 key 那页。

在源码树里实测（`--no-open`，不扫码、不联网）：`--no-open` 会把本地地址**打印出来**（"复制到浏览器里
打开就行"）；页面能 curl 到，上面有 `app_id` / `飞书` / 探针命令；**Ctrl-C 之后它自己收工**（第 21 轮
那个"中断就收手"的修复，在 CLI 这一层是生效的）。

### 第 29 轮：把"run 端上来的是飞书那页"验到**装好的树**上（顺手记一个 shell 教训）

第 28 轮是在源码树里验的，这轮在同一棵**真装出来**的树（升级演练留下的那棵）上重验了一遍：
`butler run --no-open` → 打印本地地址 → 页面上 `app_id`×3 / `飞书`×2 / `smoke.mjs` / `save` →
`SIGINT` → **自己收工**。结论一致。

⚠️ 上面这段**判读是错的** —— 第 30 轮才查清那个"子壳"其实是**命令替换**的子壳，真正的元凶是标题里
的反引号。留在下面当作一次误诊的标本。

教训（值得记）：**后台起进程时别拿 `$!` 直接当那个进程的 pid**。第一次把这一步写进脚本时用的是
`cmd & RUN_PID=$!`，脚本卡在"等页面地址"上（实测：挂了 27 分钟没人管，那个 `butler run` 还活着）。
手工验的时候用的是把后台放进一个**专门的子壳**、并在那个子壳里取 pid 的写法，拿到的是真跑
`cli.js` 的那个 pid（`bin/butler` 末尾是 `exec node …`，一路同一个 pid）—— 这个写法是对的，留下了。
**但它当时并不是卡死的原因**（见第 30 轮）。

### 第 30 轮：那个"绕过重定向的输出"查清了 —— 是**我们自己标题里的反引号**（命令替换）

第 29 轮记的"还没弄清的小现象"（`butler init` 的输出越过重定向印出来）和两次脚本卡死，**是同一个
根因**：`step "… `butler init` …"` 里那对**反引号** —— 它落在**双引号**里，于是 shell 在**拼这行
标题的时候**就把命令**真跑了一遍**（命令替换）。第 ⑧ 步的标题里写的正是 **`butler run`**，所以：

- "脚本卡在等页面地址上"是假象 —— 它卡在**命令替换里**，等一个**没人管的 `butler run`**；
- 那个活了 27 分钟、`ps` 里显示成 `sh scripts/verify-upgrade.sh` 的"子壳"，就是命令替换的子壳；
- `run.log` 根本没被创建：那行还没执行到。

先验了**产品**没有这个问题：源码 CLI 和装好的启动壳，`init > 文件 2>&1` 都是一条不漏地进文件
（14 行 / 14 行），终端上一条都没有。这是**脚本作者**的错，不是管家的错。

修法与留下的东西：

- 标题里的命令名改用「」（`⑥ 升级后「butler init」…`），并在脚本头部的**纪律**里写明这条；
- 全仓扫过 `scripts/*.sh` + `install.sh`：**只有这一处**是真的（另两处命中的在注释里 —— 注释里的
  反引号不执行）；
- 顺带发现这个坑**这个仓库早踩过一次**：`install.sh` 的 heredoc 里漏转义过一个反引号，教训就记在
  `scripts/make-installer-bundle.sh` 的注释里 —— 只是那条教训没传到别的脚本。这次它进了脚本抬头的
  "纪律"，而且**第 ⑧ 步被请回了脚本**：现在"`run` 端上来的是飞书那页"是**常设验收**，不再是手工实测。

### 第 31 轮：升级之后"程序本体"真的换了吗（merge 安装最容易糊弄过去的一条）

`install.sh` 是 **merge**（`mkdir -p "${APP}"`），不是 wipe。于是"升级"有两种假象：新东西来了，可
**跑的还是旧的**。这一轮先按**包名**把两个发布包比了一遍（`gh release download` 两个 installer 包，
`tar tzf` 出各自的 tarball 清单再比）：

- 0.1.0 有 **15** 个包名、0.2.0 有 **17** 个，多出来的是 `channel-feishu` 和 `dsh-plugin`；
- **没有任何包名消失** ⇒ 不存在"老版本独有的僵尸包"（`@butler/*` 下的目录不会平白多出来）。

所以该盯的不是"多了什么"，而是"**同名的包有没有被真的换成新版本**"。演练里于是加了三句断言：

- 升级**前**：cli 版本必须是 `0.1.0`（否则这个演练的前提就不成立）；
- 升级**后**：cli 版本必须**不再是** `0.1.0`，并把它打印出来；
- 升级后：`@butler/*` 里**不许**还有任何 `0.1.0`，不在那个作用域下的 `wechat-agent-bridge` 一起看。

结果：`✓ 程序本体真换了版本：0.1.0 → 0.2.0`、`✓ 树里没有残留的老版本包`。演练的 ✓ 从 19 条变成
**21 条**，`EXIT=0`。"升级真的会把程序换掉"这条以前没人验过 —— 第 27 轮验的是"新文件来了 + 用户的
东西没动"，那是两回事。

### 第 32 轮：探针存凭据的地方，和 CLI 读的地方，是同一条约定吗

这一轮问的是"用户扫码那一刻"的**另一条缝**。凭据按**配置所在目录**找（`cli.ts:291` 是
`butlerDir: dirname(args.config)`），所以用 `--config /别处/config.json` 的人，家在 `/别处`；
而探针默认往 `~/.butler` 写 —— 引导页给的那条命令**没带 `--home=`**：

- 用户照抄 → 凭据存进 `~/.butler/state/secrets.json`；
- `butler run` 去 `/别处/state/secrets.json` 找 → "还没有 app_id"；
- 而他刚刚亲眼看见探针说"存好了"。

**两个包各自的测试都是绿的，合起来却不通** —— 这正是 `cli/test/probe-contract.mjs` 存在的理由
（它当时带了 `--home=`，验的是"写进去的、CLI 读得出来"）。漏的是**另一条缝**：命令**本身**。

有意思的是**插件**那边早就知道这件事（`index.ts` 的报错里写着"如果你用 `--config` 把家安在别处，
给探针也要加 `--home=<那个目录>`"）—— 只有 CLI 引导页那条命令没说。

修法与留下的东西：

- `probeCommand(butlerDir?)` / `scanHint(butlerDir?)`：家**不在默认位置**时命令自带 `--home="…"`
  （带引号，路径里有空格也不散架）；默认位置一个字不加，让最常见的那句话保持最短。
- CLI 的凭据提示从"模块加载时定型的常量"改成 **`hint(butlerDir)` 函数** —— 常量在加载时就定型了，
  那时候家在哪还不知道；引导页现在**现算**一次。
- 插件那条报错也改成按自己的 `home` 现算，并且只在"家不在默认位置"时补一句"那个 `--home=` 别删"。
- 三条缝各一条测试，其中最硬的一条是把引导页算出来的命令**原样交给 shell 跑一遍**（连引号一起验），
  再用 CLI 的读法读回来。
- 反验：把"永远不加 `--home=`"种进去 → 飞书包 **3 条红**、CLI **2 条不同的红**（端到端那条 +
  凭据提示那条）；还原后 0 红。全仓 **938** 个用例、17 包、0 失败。

### 第 33 轮：报告里的人家，是**那个**人家吗

第 32 轮修好了"用户扫码那一刻"，这一轮顺着同一条线往下问：`--config` 把家安在别处的人，
**别的命令**说的是哪个家？一查就查到 `butler report`：

```ts
const butler = join(home, '.butler');                                 // 永远默认那个家
const configPath = opts.configPath ?? join(butler, 'config.json');    // 配置路径倒是尊重 --config
```

于是同一份报告**自己跟自己打架**：①段在数 `~/.butler` 里的文件（凭据"有没有"这一句是假的），
②段读的却是 `--config` 那份配置，④段的 `doctor` 也是读 `--config` 那份。而 report 是
"出事了、把这一份发给帮你的人就行"那份东西 —— **指错地方比不写更坏**：帮忙的人照着它去找，
找不到，还得再问一轮"你确定是 `~/.butler` 吗"。

修法只有一条规则：**管家目录 = 配置所在目录**（和 `cli.ts` 里 `butlerDir: dirname(args.config)`
同一条）。

- `report.ts`：`butler = dirname(configPath)`。默认安装一个字节没变（默认配置本来就在 `~/.butler` 下），
  但"别处那个家"现在说的是真话。
- **自启动日志**是唯一**不该**跟着走的：`autostart.ts` 里它永远写在 `~/.butler/logs`。所以报告那一行
  **如实**说它不跟着 `--config` 走，而不是顺手拼到新管家目录后面（那样会指一个不存在的文件）。
  顺手把这条路径抽成 `autostartLogFile(home)` —— 自启动写它、报告念它，两处按同一条规则；
  抄两遍就迟早有一遍过期。
- `autostartOn` 里那句"日志：~/.butler/logs/autostart.log"也改成按这条规则算（默认用户看到的一字不变）。

⚠️ 这一轮又撞出一个**测试比法太死**的例子（和第 32 轮同一类，但原因不同）：新测试一开始比"整条
路径"，红了 —— 而红的不是产品，是**报告的脱敏器**把 macOS 临时路径里那串长随机段按"像密钥"隐去了
（`管家目录：/（长串已隐去）-report-8QWkwe/别处的家`）。产品是对的，是比法太死；改成比可辨认的
尾巴（写死 `~/.butler` 时那一行里根本不会出现"别处的家"，仍能证伪）。顺带在报告第 ⑥ 段加了一句
人话：**隐去是按形状扫的，路径里又长又随机的串也会被隐去，读起来断一截是正常的**。

反验：把 `butler` 改回写死的 `~/.butler` → 那条测试当场红（报出的正是 `管家目录：…/.butler`）；
还原后 report + autostart **20 条全绿**。全仓 **939** 个用例 / 17 包 / 0 失败。

⚠️ 同一轮顺手记下一个**没修**的（暴露面低，先记着）：`BUTLER_HOME` 这个环境变量**只有探针认**
（`--home=` > `BUTLER_HOME` > `~/.butler`），CLI 完全不认它 —— 有人一旦 `export` 了它，就成了第 32 轮
那个坑的**镜像版**（探针存到 `$BUTLER_HOME`，CLI 读 `~/.butler`）。它**没有任何文档**提过，所以只有
读过探针源码的人才会踩。两条路：要么让 CLI 也认它（改动面大 —— autostart / report / 各处默认值都得
跟着走），要么干脆从探针里去掉。留着这一段，是因为它现在是一条**已知的、写下来的**不一致，
而不是没发现的那种。

> ✅ **第 37 轮修了**（选的是"让 CLI 也认它"）。当时估的"改动面大"其实**被第 35 轮那次改动消掉了**
> —— 那一轮把 `autostartLogFile(home)`、`scanHint(butlerDir)`、`probeCommand(butlerDir)` 的参数
> 全改成**必填**，默认值就只剩 `butlerHome()` / `DEFAULT_CONFIG_PATH` / `defaultHome()` 三处，
> 于是这一轮改三行就齐了。

### 第 34 轮：手册教人改的那个文件，**根本不存在**（"认主"从来没落过盘）

起点是**照着手册自己走一遍**：§十二 第 5 步说"想彻底钉死，就把探针打印的 `senderId` 写进
`<管家目录>/state/state.json` 的 `owner`"。可真装的 `~/.butler/state/` 里只有 `cursor.json`、
`memory.json`、`token.json` —— **没有 `state.json`**。手册在教人改一个不存在的文件。

往下一查，根子比"文档写错"深：`SessionStore`（`packages/core/src/sessions.ts`）的 `file`
**给了就落盘、不给就纯内存**，而 `butler init` 生成的内核行**只给了 `workspace`** ——
一个字节都没落。于是两件事同时成立：

1. 手册那条"钉死主人"的做法是**空话**（写进去没人读，文件也不会被建出来）；
2. 更要紧的是**认主本身不持久**：重启之后第一个说话的人又成了主人。企业租户里 `dmMode`
   默认是 `open`（同一家公司谁都能单聊它）—— 而 §十二 自己刚警告过这件事。

**为什么一直没被发现**：每一处测试都**自己传了 `stateFile`**（`doctor.mjs` 的注释甚至写着
"真内核要 workspace 和 stateFile"）—— 测试都写死了，生产没写。（第 32、33 轮是同一家族的
另一面：测试的假设比产品还硬；这轮反过来，测试比产品**更严**，却谁也没去问"生产给了吗"。）

修了三件事：

- **生成的配置**：内核行现在带 `stateFile`，指向 `<管家目录>/state/state.json`。理由和紧挨着的
  通道行一模一样（那行的注释里就写着"**必须钉住**：不写它就落在当前工作目录"）—— 所以那条
  新用例钉的是"必须是绝对路径、必须落在管家目录里"，而不只是"字段在不在"。
- **老配置**：`topUpRows` 顺手补上**缺**的这个字段（同一道门：只认我们自己生成的那份；而且
  **只在字段缺失时补** —— 用户写过的值哪怕是一个空串也一个字不动，他可能就是想说"别落盘"）。
  用户在 §十二 第 5 步跑的那条 `butler init --im feishu` 就会把它补上。
- **说实话**：`doctor` 的"谁能指挥它"和 `run` 的开局提醒，都会在 `stateFile` 缺失时当场说破
  （"认主**没落盘**：重启之后第一个说话的人又会成为主人"），并给出那一步。原先那句
  `删掉 ${stateFile || 'state.json'} 重新认主` 更是**指向一个不存在的文件**，一并改掉。

测试：`packages/core/test/sessions.mjs`（**新建** —— 这个类以前**一条直接用例都没有**，
尽管它是"认主"唯一的持久化机制）钉住"给了路径就落盘、换一个实例还记得"、"不给路径就纯内存"、
"手册教人**手写**的文件必须被认、写坏了也不许让内核起不来"；`setup.mjs` 钉住"生成的配置里
那个路径是绝对的、在管家目录里"和"老配置补得上、写过的值不动"；`core.mjs` 钉住"没落盘时要说破"。

反验（三处独立变异，各自命中，不含糊）：① 生成的配置不钉 `stateFile` → 2 红（新用例 +
"配置齐全时 `run` 不该啰嗦"）；② 补漏时报了成功却没真写进去 → 1 红；③ core 的自检谎称"落了盘"
→ 1 红。还原后全仓 **946** 个用例 / 17 包 / 0 失败。

⚠️ 修的过程里连着踩了两个**同一类**的坑，都由新测试当场抓住：第一版把补漏那段放在
`if (!missing.length && !next) return` **后面**（"行齐、通道也对"的老配置恰好什么都不缺，
于是永远走不到那里）；补完字段又忘了在 `initButlerHome` 的返回里**挑**出来（那个返回是逐个
字段拼的）。记下来是因为它说明一件事：**"加一个字段"要检查的地方比直觉多两处** ——
写入点、返回值的拼装点，以及调用方要不要念给用户听。

⚠️ 顺手记一个**不是这轮改的**抖动：全量并行跑时，`channel-wechat` 那条"收信循环"用例
（自带 25 秒超时）偶发红一次，报的就是 `Error: 等待超时`。判据是同一份源码**上一次全量全绿、
单独跑这个包也全绿** —— 所以是并行负载下的抖动，不是这轮碰出来的。写在这里，免得下次
看到它红的时候又从头查一遍。

⚠️ 还顺手记一个**同一族、没修**的：内核的授权文件路径也是从 `stateFile` 派生的
（`grantsFileOf`：`dirname(stateFile)/grants.json`），而 `stateFile` **为空**时它退回
`<homedir>/state/grants.json` —— 那是**管家目录之外**的一个目录（`~/.butler/state/` 才是它
该在的地方）。第 34 轮之后新生成的配置都带着 `stateFile`，所以这条只在**手写的、没有那个
字段的**配置上才踩得到（真装的机器跑一次 `butler init` 就补上了）。先写在这儿：它现在是一条
**已知的**不一致，而不是没发现的那种。

### 第 35 轮：排练第 ⑤ 步 —— "照抄那条命令"抄到的是**错的地方**

还是从**照着手册自己走**来的（第 34 轮也是）：把 §十二 第 ⑤ 步（`butler init --im feishu`
→ `butler run`）在一台临时家里原样走了一遍。`init` 的输出、`doctor` 的自检、那句"还没认主"
都对 —— **第 34 轮修的 `stateFile` 在真流程里看得见**（内核行带着它，`doctor` 也不再补那句 ⚠️）。

露馅的是那条"扫码最省事"的命令：把家安在别处（`--config`）时，它**没带 `--home=`** ——
**`init` 的引导页和 `doctor` 的自检都漏了**。用户照抄一遍，凭据落进 `~/.butler`，而 CLI 在别处读：
现象正是第 32 轮修过的那句"探针说存好了，`butler run` 却说还没有 app_id"。

根子在签名：`scanHint(butlerDir?)` / `probeCommand(butlerDir?)` 的管家目录是**可选参数**，
第 32 轮加它的时候只改对了**两个**调用点（适配层报错、CLI 的凭据提示），另外三个漏传 ——
TypeScript 一声没吭（可选参数，不传合法）。**这就是"随手加个可选参数"最贵的那种代价。**

所以修法不止"把那三处补上"（那样下次还会漏）：

- `probeCommand` / `scanHint` / `autostartLogFile` 的管家目录改成**必填** —— 编译器从此替我们
  盯住每个调用点（改完立刻抓出第四处：`index.ts` 里长连接失败那句）。
- 补三处：`connectFailed` 收下 `home`；`check()` 用 `this.home`；`init` 的引导页用
  `dirname(r.configPath)`。
- 顺手审了同一族（`credentialsFileOf` / `keyRefOf` / `approvalsDir` / `reportFilePath`）：
  它们的"家"要么必填、要么由**行里带着的 `home`** 送进来，没有第二个漏点。

测试那条**不碰函数**：真跑一次 `butler init --config <别处> --im feishu`，从**输出**里把命令
抠出来（连引号一起），原样交给 shell，再问 CLI 读不读得到。参数、默认位置判断、输出格式，
改坏哪一处它都会红。（第 32 轮那条契约测试是**手写** `--home=` 去调函数的 —— 所以它一直绿，
漏掉的恰恰是"用户手里那句话"。）插件那条**宽容**的正则也换成**明确**断言：别处的家必须带
`--home=`；`plugin.mjs` / `tarball.mjs` 里两处无参调用改成显式传默认家。

反验：把 `cli.ts` 那处改回 `scanHint()`（= 第 35 轮之前的样子）→ 新用例当场红，报出的正是
"别处的家必须带上 --home="。全仓 **947** 个用例 / 17 包 / 0 失败。

⚠️ 另记一件**不是这轮改的**：`cli` 套件里那几条自带 25 秒超时的用例，在和别的包并行跑、
这台机器又被构建压着的时候偶发红一次（判据同样是"同一份源码单独跑全绿"）。这一轮新加的那条
测试会真起一次探针去连网（`--save` 是**存盘在连接之前**的，被超时杀掉是预期结局），
它让这套件的负载又高了一点 —— 写在这儿，免得下次从头查。

### 第 36 轮：把"没跑通的样子"也走了一遍 —— 手册只写了跑通的样子

上一轮修完，`run` 那条路上还剩**最后一截没人走过**：凭据有了、模型 key 也有了，`core.start()`
真的去连飞书那一步。这一截不必等真租户 —— 拿**假凭据**连一次真的官方长连接，看到的失败形态
就是真机的失败形态（第十二节表里那句 `not_connected` 本来就是这么抓到的）。

怎么走到那一步：`ensureModelKey` 有一条环境变量近路（`DEEPSEEK_API_KEY` 在启动环境里就直接过），
所以临时家里带上它 `butler run --no-open` 就能一路走到上线。看到的是：

> `[info]: [ 'client ready' ]` ／ `[info]: [ 'event-dispatch is ready' ]`
> `起不来：连不上飞书的长连接：could not resolve bot identity via /open-apis/bot/v3/info —`
> `required for channel to function（code: not_connected）。两种可能…出路：扫码最省事：…`
> `插件都装上了，是"上线"这一步没过 —— 上面那句就是原因。`

三件事因此**被确认**（都不是猜的）：

1. **它自己退出** —— 不挂在那儿、不循环重试。用户不会对着一动不动的终端等。
2. **这条路上一个 URL 都没有**：官方那句原文里夹着一条**签名的一次性授权链接**，适配层把它剥掉了。
   这正是第十一节那条要求（`consoleUrl` 等同于凭据）。原来那条测试验的是**合成**的
   `SECRET-TOKEN`，这次是**真**报错 —— 断言因此加强成"这条消息里一个 URL 都不该有"。
3. 那两行 `[info]: …` 是官方 SDK 自己的日志（"就绪"只是本地客户端起来了），偏偏紧跟在失败之前，
   很容易被当成原因 —— 而手册原来**一个字都没写**它们。

改动：`plugin.mjs` 那条测试补两条断言（`--home=` 必带 —— 它是同一族里**第三处**漏传管家目录的
调用点，第 35 轮修好了却没有断言盯它；以及"不许有任何 URL"）；手册的"看到什么 → 大概率是什么"
表补两行（那两行 `[info]`、以及"插件都装上了"那句意味着失败在**连接**上），并在"凭据不对"那行的
"怎么办"里把"这条路上不会出现任何 URL"写明。

反验：M3 让 `connectFailed` 传默认家 → `--home=` 那条断言红；M4 把官方 `context.consoleUrl`
缝进消息 → "不许有任何 URL"那条红。用例总数不变（**947** / 17 包 / 0 失败 —— 这两条是往已有用例
里加断言，不是新用例）。

没做的（记在这儿）：官方 SDK 那两行 `[info]` 只是**写进手册**，没有去关掉它 —— 那是人家客户端的
日志，关它属于另一件事，得先想清楚要不要动官方包的行为。

### 第 37 轮：`BUTLER_HOME` 是**第四个**说"家在哪"的地方 —— 让它和另外三处说同一句话

第 33 轮把它记成"已知未修、暴露面低"。这一轮真去复现了一遍，发现它比"路径不统一"要重：

> 探针（`--save`）会对用户说："**凭据已存进 `/data/butler/state/secrets.json`（0600）—— 下次
> `butler run` 选飞书时会直接用它，不用再扫。**"

而 CLI 读的是 `~/.butler` —— 设了 `BUTLER_HOME` 的人拿到的是一句**假承诺**，紧接着就是那句熟悉的
"探针说存好了，`butler run` 却说还没有 app_id"。复现里还看到更钝的一面：`init` 把**全新的**配置
写进 `~/.butler`，`doctor` 于是说"实际读的文件：`~/.butler/config.json`"、装载全 ✓ —— 一切正常，
而凭据在另一个家里。

改的是**那条规则**，不是某一处：家 = `$BUTLER_HOME` > `~/.butler`，四处一起认 ——

| 谁 | 之前 | 现在 |
| --- | --- | --- |
| 探针 `probe/save.mjs` 的 `homeOf` | 认 `BUTLER_HOME` | 不变（它是基准） |
| `cli/src/setup.ts` 的 `butlerHome()` | 只认 `~/.butler` | 认 `BUTLER_HOME` |
| `cli/src/setup.ts` 的 `DEFAULT_CONFIG_PATH` | **常量**，import 那一刻定死 | 换成函数 `defaultConfigPath()`：常量会在测试设环境变量**之前**就把家定死 |
| `channel-feishu/src/probe-path.ts` 的 `defaultHome()` | 只认 `~/.butler` | 认 `BUTLER_HOME` |

`DEFAULT_CONFIG_PATH` 由常量换成函数之后，编译器把**四处**调用点一次找齐（`cli.ts` 的解析器默认值、
`cli.ts` 里"要不要印 `--config`"、`setup.ts` 的兜底、测试里的断言）—— 第 35 轮那条教训：**别用可选
参数或常量，让编译器替你数**。

两条新用例（跨两个半球的那条才是契约本身）：

1. **单元**：设了 `BUTLER_HOME` → `butlerHome()` / `defaultConfigPath()` / `defaultPatchPath()` 全换
   过去；**空串 / 空白 = 没设**（`BUTLER_HOME= butler run` 是很常见的写法，不能因此把家搬到 `""`）。
2. **跨半球**（`probe-contract.mjs`）：`BUTLER_HOME=<临时家>` → `init`（不给 `--config`）→ 从它印出来
   的命令里抠出探针那行 → **原样粘进 shell** 跑一遍 → 凭据落在那个家里 → 再用 **CLI 自己的读法**
   （`readSecrets`）读回来 ⇒ 探针那句"下次 `butler run` 直接用它"**兑现**；并且那条命令**不带**
   `--home=`（它就是默认家，保持最短）；再加一条：显式 `--config` 仍然**压过**环境变量。

反验三处，每处都红在该红的那条断言上：

- **M1** `butlerHome()` 不认环境变量 → 单元那条报 `actual: '/Users/leo/.butler'`；跨半球那条报
  "设了 BUTLER_HOME，init 就该把家安在那儿（不是 ~/.butler）"。
- **M2** `defaultHome()` 不认环境变量 → **只有**"不必带 `--home=`"那条红，并原样打出两边各执一词的
  那条命令（`--home="/var/folders/…/data"`）；同一时刻 `setup.mjs` **30/30 全绿** —— 变异只碰了探针那半。
- **M3** `init` 无视 `--config`、永远用默认家 → 红两条：一条是"`--config` 比 BUTLER_HOME 优先"，
  一条是第 35 轮那条"别处的家必须带上 `--home=`"。

顺手补上一处**发现性**的缺口（第 33 轮那句"它没有任何文档提过"的剩下半边）：`butler --help` 里

### 第 43 轮：最后两处 —— 报告和自启动

第 42 轮结尾自己记下了"没做的"：`cli/src/report.ts` 和 `autostart.ts` 里还有几处把家算成
`$HOME/.butler`。这一轮收了它们，顺带把那条规则的用法说清楚 —— 因为**坑就在用法上**。

这两处都长这个样子：

```ts
const home = opts.home ?? homedir();                            // ← 操作系统家目录
const configPath = opts.configPath ?? join(home, '.butler', 'config.json');
```

`opts.home` 是**操作系统家目录**（测试用它把家安在临时目录里；`autostart` 还要拿它去拼
`~/Library/LaunchAgents`，那个**必须**是真家）。所以"把 `homedir()` 换成 `butlerHome()`"这种
改法是错的 —— 它会连 `~/Library` 一起搬走。正确的改法是**新增一个 `butlerDirOf(opts.home)`**：
给了 `opts.home` 就用 `<它>/.butler`，没给才轮到 `butlerHome()`（`$BUTLER_HOME` > `~/.butler`）。

⚠️ **传进去的必须是原始的 `opts.home`（可能是 `undefined`）**，不能是 `opts.home ?? homedir()`
的结果 —— 后者在没给 `home` 时已经是一个具体的家目录字符串了，于是 `BUTLER_HOME` 又被悄悄丢掉，
正好是这一轮要修的毛病。这条注意写在 `butlerDirOf` 的注释里。

顺带把 `.butler` 的拼接收成一处：`autostartLogFile()` 的参数从"操作系统家目录"改成"**管家目录
本身**"（那两处显示、写盘的调用点一起改），于是"拼 `.butler`"全仓只有 `butlerDirOf` 一处。
`report.ts` 里那两句"这一条不跟着 `--config` 走"仍然成立（日志不跟 `--config`），但**要跟
`BUTLER_HOME`** —— 那就是"家在哪"。

反向验证踩到自己一个坑，值得记下来：第一版断言写的是 `plan.content.includes(HOME)`，把
`autostart.ts` 那行改回旧写法后**竟然还是绿的** —— 因为自启动单元里还有日志那一行，它也含

没做的：真机验收（真飞书企业里扫码、长连接、回一条消息）。

### 第 44 轮：凭据存好了、配置里却没那条通道 —— 这一路**不报错**，所以必须自己说出来

第 43 轮收尾时登记的"没做的"里有一条：**盘上存了凭据、但那条通道不在配置里时，运行时该有句提示**。
这一轮把它做了 —— 它是验收入口上最容易走进的那个死胡同。

**实测复现（修之前）**：临时家里 `init`（默认那份配置只有微信那行）→ 往 `state/secrets.json` 写一份
**完整**的飞书凭据 → `butler doctor`：全部 ✓，装载里只有微信那行，「飞书」和「app_id」各出现 **0** 次。
`butler run` 也一样：管家正常起来、消息发出去**没人应**。用户这时候最容易怀疑的是"是不是我权限没配
好"，然后去开发者后台折腾半天 —— 而真正少的是那条 `butler init --im feishu`。

**为什么"不报错"是这里最坏的性质**：探针那条路（`--save`）的最后一步就是把凭据存进
`state/secrets.json`，而通道要在**配置里有一行**才会被装载。少跑一次 `init` 的后果不是红字，是安静。

**修法**：`secrets.ts` 里加 `unpluggedChannels({ butlerDir, rows })` —— 走的是**同一张 `NEEDS` 表**
（"一个通道要哪几项凭据"从第 32 轮起只写在那儿），反向查一遍：某条通道的凭据**每一项都非空**、而配置
里没有它的行 → 报出来。`label` 和 `im` 都从那两项推出来，所以**以后加通道时这里一行都不用改**。

- **只认"齐了"**：只存了 `app_id`、`app_secret` 还没扫到时**不吭声** —— 那时候他手上的事还没做完，
  催他去 `init` 只会让人以为哪里错了。反向验证就是拿这条做的（`every` → `some` ⇒ 用例 ④ 立刻红）。
- **关掉的行也算"配置里有它"**：用户是**主动**关的，不该再催他 init。
- **认不出来的通道不瞎指路**：微信那条插件不靠 `--im` 换（也不在 `NEEDS` 里），所以不猜它的命令。

**一句话，两处打印**：`unpluggedHint(u)` 是那句话的**唯一**一份 —— `butler doctor` 的装载段、
`butler run` 的"读配置"之后各打一次。第 41 轮的教训就在这儿：同一句话抄两遍，迟早有一遍过期。

**验证**：`secrets.mjs` +2 条（四个分支：齐了 / 已有那行 / 关掉那行 / 只扫了一半，外加 Telegram 一条），
`doctor.mjs` +1 条 —— 既要 `r.unplugged` 有值，也要 `formatDoctor` 的文本里真有那句话（只看字段的话，
"检测对了但忘了打印"照样绿）。**反向验证**两道，都咬得住：① `every` → `some` ⇒ secrets 那条红
（半份也被报出来）；② 把 doctor 那句打印换成占位 ⇒ doctor 那条红（"报告里要有这一句"）；恢复 ⇒ 全绿。
另外手验了一次 `run` 路径（`HOME` 指向临时家、零网络）：那句话印在**第 3 行**，正好在"读配置"之后、
"装载"之前。

**没做的（这一轮）**：真机验收还是等你那一枪（同前）。另外这句话**不替用户做决定** —— 只说下一步，
**不会偷偷往配置里加行**：改他的东西是 `init` 的事，不是 `run` 的。

> ⚠️ 顺带记两个**验证工具**上的坑（第 44 轮自己踩的）：① 全量验证那次是**用 `&` 野起**的，
> pnpm 给每个包的输出加了 `packages/<包> test: ` 前缀，于是按列取的 `awk '{s+=$3}'` 取到的是 `test:`，

> 任务起。

### 第 45 轮：官方 SDK 的日志 —— 别用"全静音"冒充"降噪"

终端里混着一堆官方的 `[info]: [ 'client ready' ]`，我们自己那句话（"长连接已建立。机器人身份：…"）
被淹在里面。看着像"把 `loggerLevel` 调成 `warn` 就行了" —— 官方 README 那张表就是这么写的
（`logger` / `loggerLevel`，默认 `info`）。**照着做会把官方日志整个弄哑。**

**实测**（源码树里真跑出来的，不是推理）：

| 传什么 | 我们的 logger 收到 |
| --- | --- |
| 什么都不传 | 2 条 `info`（`client ready`、`event-dispatch is ready`）—— 走的是 `console.info` |
| 只传 `logger` | 同样那 2 条，**送进我们的 logger** ✓ |
| `logger` + `loggerLevel: 'warn'` | **0 条** |
| `logger` + `loggerLevel: 'info'` | **0 条** |

根子：`LoggerLevel` 是个**数字**枚举（`fatal=0`、`error=1`、`warn=2`、`info=3`、`debug=4`、`trace=5`），
而 README 那张表写的是 `info` 这种**字符串**。字符串跟任何枚举值都不相等 ⇒ 一条都不打，连 warn/error
都没了。而且 `LoggerLevel` 运行时**没有**从 `@larksuite/channel` 导出（`import { LoggerLevel }` 直接
`SyntaxError`），想传对都不好传。

所以这一轮的做法是：**给它一个 logger，不碰 `loggerLevel`**，级别分流由我们做 ——

- `error` / `warn` → 原样进 `ctx.logger`（官方报的错必须看得见）；
- `info` / `debug` / `trace` → 降一级到 `debug`。Cordis 的 logger 默认级别是 `info`（实现里就是
  `this.level ?? 1`），所以这一级**默认不打印** —— 实测：真管家上下文里跑 `doctor`（那一步会构造
  官方通道），官方那两行 `[info]` **一行都不出现**。级别本身是可调的 —— **第 46 轮补上了那个开关**
  （`BUTLER_LOG_LEVEL=debug`）。

`larkOptionsOf(config, log)` 是交给官方的那份选项，抽成**纯函数**只为可测：注释挡不住下一个人顺手加
一行 `loggerLevel`，用例挡得住。探针（它没有 Cordis 的 logger）用同一套规矩，另外加了 `--sdk-log`
把官方日志全放出来（查问题时用）。

**验证**：新文件 `test/sdk-log.mjs` 4 条 —— ① 分流表（顺带钉住"整条当对象打"：官方参数里可能带
`%s`/`%d`，当格式串拼进去会被再解释一遍）；② 没有 logger 也不炸；③ **交给官方的选项里有 logger、
没有 `loggerLevel`**（顺手钉住既有的"空白名单不传 groupAllowlist"）；④ **钉住官方行为** —— 它真会
把日志送进传入的 logger，而多一个 `loggerLevel` 就全灭（哪天官方把字符串也认了，这条会红，我们
就知道可以简化）。真造一个适配层通道时，终端里**一行 `[info]` 都没有**。

**没做的（这一轮）**：
- 探针的 `registerApp`（扫码注册）那段**不认** `logger` 选项，所以扫码过程中官方可能还是插一两行
  —— 那是它自己的 logger，我们够不着（**没验**：真连一次才知道它到底打不打）。
- 没给"日志级别"加配置项：默认安静、warn/error 照出已经够用，再多一个旋钮等于多一处会漂的地方。
  ⚠️ 代价说清楚：`info`/`debug`/`trace` 那三级现在**递到了** logger，而这台机器的默认级别（`info`）
  会把它们压掉。

  ✅ **（第 46 轮补）** 上面那句"眼下只有探针的 `--sdk-log` 这一条路"已经不准了，一并记在这儿：
  第 46 轮发现整个 `ctx.logger` **根本没往终端打**（Cordis 默认那个 exporter 只往内存里塞），
  于是补了一个终端 exporter 和 `BUTLER_LOG_LEVEL` 这个开关。现在真要看官方那几行，说
  `BUTLER_LOG_LEVEL=debug` 就行。

### 第 46 轮：插件自己的日志，其实**从来没有被打印过**

上一轮把官方 SDK 的日志接进了 `ctx.logger`（info 降一级、warn/error 照原样出），并在文档里写下
"warn/error 必须看得见"。这一轮去验那句话 —— 结果发现**整个 `ctx.logger` 都没人打印**。

Cordis 的 `Context` 一建起来就替 `ctx.logger` 装了一个**默认 exporter**，而它只做一件事：

```js
(message) => {
  self.buffer.push(message);
  if (self.buffer.length > self.bufferSize) self.buffer = self.buffer.slice(-self.bufferSize);
}
```

`bufferSize = 1e3`，环形，**没有读者**。所以这些行全都掉进了一个没人看的缓冲：

- `feishu: 上线了（机器人身份：…）` —— 验收手册让你看的那句；
- `[core] …`、`[agent-dsh] 启动：profile=…`；
- 官方 SDK 报的错（上一轮刚接进来的那些）。

实测（三处，都不是推理）：

| 怎么看 | 结果 |
| --- | --- |
| 真 `butler run`（临时家 + 假凭据）的输出 | `feishu:` / `[core]` / `[agent-dsh]` **0 行** |
| `boot()` 之后直接 `ctx.logger.info(...)` | 终端上**什么都不出**（而 `ctx.logger.exporters` 里确实躺着 1 个） |
| `logs/autostart.log`（自启动那个文件） | 也收不到 —— 它接的是进程的 stdout/stderr，而这些行从没走到 stdout |

**没有报错，也没有任何提示** —— 正是这个项目一直在防的那类：看起来正常，其实是哑的。

做法：`boot()` 里再挂一个**往终端打**的 exporter（默认那份留着不动），级别由 `BUTLER_LOG_LEVEL`
定，默认 `warn`：

| 取值 | Cordis 的数字 | 能看到 |
| --- | --- | --- |
| `error` | 0 | 只有 error |
| `info` | 1 | error + info —— **不含 warn**（Cordis 的排法是 `info=1 < warn=2`，反直觉） |
| `warn` | 2 | error + info + warn ← **默认** |
| `debug` | 3 | 全都，含 debug（官方 SDK 的 info 就降在这一档） |

两个细节：`warn`/`error` 走 **stderr**（管道里能和正常输出分开），`info`/`debug` 走 stdout；
**不加前缀** —— 这个仓库每条日志都自带前缀，而 `message.name` 一律是服务名 `logger`（实测），
再拼一遍只是噪声。取值不认识时**明说一声**再按默认来（`BUTLER_LOG_LEVEL=deubg` 会得到
`⚠️ BUTLER_LOG_LEVEL=deubg 不认识，按 warn 来（可选：error / info / warn / debug）`）。

**这一轮也把上一轮那句话坐实了**：`BUTLER_LOG_LEVEL=debug` 跑 `doctor`，终端上真的出现

```
feishu sdk: [["client ready"]]
feishu sdk: [["event-dispatch is ready"]]
```

—— 官方 SDK 那两行，现在**够得着了**（上一轮只是"递到了 logger"，够不着）。

**验证**：新文件 `test/logging.mjs` 5 条 —— ① 级别表（含"不认识要出声"）；② 挂上之后三条的流向
与级别过滤；③ `debug` 档放行最低一级；④ **摘掉之后就不打了**（`ctx.logger.exporter()` 返回的
disposer 真管用）；⑤ **`boot()` 里已经挂好了**（装完插件直接 `ctx.logger.info` 就能到 stdout）。
反向验证两道：把 `boot()` 里那行挂载注释掉 ⇒ 第 ⑤ 条红（消息里直接给出"实际收到：[]"）；把级别
写死成 3 ⇒ 第 ② 条红。恢复后 5/5 绿。

**没做的（这一轮）**：
- Cordis 自带那个缓冲 exporter **没动**（它不碍谁，也不好从外面摘）；我们只是**多挂了一个**。
- 没做**按插件分别定级**（只开了 `levels.default` 一个口子）。真需要时再加。
- 没验 DSH 图形界面那边的日志视图 —— 那条路走的是它自己的通道，与这里无关。

### 第 47 轮：把"会打印给用户看的话"做成仓库级检查（第 41 轮自己写下的"没做的"）

第 41/43 轮把"提示里出现的东西，用户手上得真有"这条规矩落在**一个包**的打包产物上，并留下最后一句
"没加一个仓库级的静态检查脚本（`check:user-facing` 之类）……别的包要不要同一条，等真有下一次撞上
再说"。这一轮把它做了 —— 而且"下一次"其实已经来了：**第 46 轮把"会打印"的集合加宽了**
（`ctx.logger.*` 以前只进一个没人读的内存缓冲，等于不打印；现在它真的会打到终端上）。

新脚本 `scripts/check-user-facing.mjs`（`pnpm check:user-facing`，CI 里一步）。规矩本身没变：

```text
凡是"会打印出去"的行里，不许出现 packages/ docs/ scripts/ —— https://… 里的路径不算。
```

两个决定值得记下来。

**一、用语法树，不用正则。** 注释里到处都是 `docs/…`（写给人看的），而 `//` 又出现在 `https://…`
里 —— 用正则剥注释**一定会剥错**。所以拿 TypeScript 的 parser 认这几类调用：
`console.log/error/warn/info/debug(…)`、`process.stdout/stderr.write(…)`、**logger 家族的
`info/warn/error/debug(…)`**（`ctx.logger.x` / `this.ctx.logger?.x` / `this.log(…)` 都算 —— 这是
第 46 轮的加宽）、以及 `.sh` 里的 `echo/printf/step/ok/bad`（脚本没有 AST，那几行纯文本扫）。
`typescript` 本来就是根上的 devDependency，没添新依赖。

  ✅ **（第 48 轮补）** 上面"认 logger 家族"这句**太窄了**，实测漏了两类：引导页的 `opts.log(…)`
  （打印口是**注入进来**的，14 处）和扫码页的裸 `log(…)`。现在改成"**任何**
  `.log/.info/.warn/.error/.debug(…)` 都算，不看接收者叫什么"；`.write` 仍然只认
  `process.stdout/stderr`（全仓数过：别的 `.write` 落在 `handle`/`store`/`state`/`res` 上，
  是写流写盘）。见第十一节第 48 轮。

**二、范围是"谁在看这句话"，不是"哪个目录"。** 第一次跑就报出 5 处命中，**全在 `scripts/*.sh`**
（`make-dsh-plugin-bundle.sh` 里的 `packages/seam-channel/lib`、`release.sh` 里的 `packages/` 和
`docs/CHANNEL-FEISHU.md`）—— 可那是**维护者工具**：跑它的人手上就有仓库，那些路径正是他自己要看的。
所以查的是"会到**装出来的用户**眼前的东西"：`packages/*/src`（CLI 与插件）、`packages/*/probe`
（探针跟着包一起发）、`install.sh`（用户的第一个入口）；**不查 `scripts/*.sh`**。圈太大只会逼人写
例外，圈太小又拦不住 —— 这条线就是"谁在看这句话"。

**它现在没抓到东西**，而这正是想要的状态：这一轮之前 `.ts`/`.mjs` 侧本来就是干净的（第 40/43 轮修过），
它守的是"以后别再出现"。它的第一个产出反倒是上面那个**范围**决定。

**验证**（六道反向验证，用 `node scripts/check-user-facing.mjs <文件>` 指向临时文件，不动仓库）：

| 喂进去的东西 | 期望 | 实测 |
| --- | --- | --- |
| `console.log('详细对照表在 docs/CHANNEL-FEISHU.md')` | 报 | ✅ `p1.ts:1` |
| `ctx.logger?.info('看 node packages/cli/probe/smoke.mjs')` | 报 | ✅ `p3.ts:2` |
| `process.stderr.write('见 scripts/release.sh 里那段\n')` | 报 | ✅ `p4.ts:1` |
| `console.error('第 ' + n + ' 步：见 docs/CHANNEL-FEISHU.md')`（字符串拼接） | 报 | ✅ `p6.ts:2` |

**收工前它还抓到自己的一个盲区。** 顺手核了一下"出包的目录是不是都扫到了"，才发现第一版只认
`.ts` —— 而 `channel-wechat/src`（12 个 `.mjs`，包括 `qr-page.mjs`、`login.mjs` 这种**专门印给
用户看**的）和 `dsh-plugin/src` 的源码就是 `.mjs`：**17 个文件被静默跳过**。改成
`.ts / .mts / .mjs / .js` 之后重扫，那 17 个是干净的（没有现行违规），但"范围名不副实"必须修；
顺便补了一条**防静默**的守卫：某个包的 `src/` 一个文件都没收到就直接报错，并点名是哪个包。

守卫自己也差点假绿：第一版判的是"这个包至少收到了一个文件"，而 `channel-wechat/src/plugin.d.ts`
是 `.ts`，正好把它满足了 —— 一个**纯类型声明**挡在门口。实测：后缀只留 `.ts` 时，守卫只点出
`dsh-plugin`，**漏了** `channel-wechat`；把声明文件（`.d.ts` / `.d.mts`）排除之后再测一次，
两个包都点出来了。这条和仓库里那句"**被邻居字符串满足的断言，不是守卫**"是同一件事。

顺带把出包范围也复核了一遍：每个包 `files` 里声明出去的**源码**文件，只有

### 第 51 轮：包自己的依赖清单，第一次跟源码对得上

`check:packages` 守的是"**装出来的包是不是完整的**"，可它只查**文件带没带走**（`files` 覆盖没覆盖），
没查**依赖声明对不对**。那是同一个病根的另一半，而且更阴：

- `files` 漏了产物 ⇒ 装出来**立刻** `Cannot find module`（响亮）；
- 依赖只写在 `devDependencies` ⇒ **本地永远跑得通**（仓库里装着、宿主也恰好声明了），换台机器或被
  别人当包用才炸（安静）。

先量源码：把 `src/` 里**值导入**的外部包，跟 `dependencies`/`peerDependencies` 对一遍。结果：**7 个包**
在运行时用了 `@deepseek-ai/schemastery`，却只写在 `devDependencies` 里 —— 而**同一批包**对
`@deepseek-ai/cordis`（一样是宿主提供的）写的是 `peerDependencies`。一样东西，仓库里有**三种**写法：

| 写法 | 谁 | 对不对 |
| --- | --- | --- |
| `peerDependencies`（＋dev） | 11 个包对 `cordis`、`dsh-plugin` 对 `schemastery` | ✓ 宿主提供的东西就该这么写 |
| `dependencies` | `channel-feishu`、`channel-telegram`、`cli`、`wechat-agent-bridge` 对 `schemastery` | 能跑，但不统一（可能多一份副本） |
| **只有 `devDependencies`** | 7 个包对 `schemastery` | ✗ 清单没说实话 |

改法：那 7 个包补 `peerDependencies` 里的 `"@deepseek-ai/schemastery": "^3.18.4"`（照 `dsh-plugin` 的
写法），`devDependencies` 留着（本地构建测试还要用）。

⚠️ **说清楚**：现在装出来的系统**本来就是好的** —— CLI 自己把 schemastery 声明成了 `dependencies`。
补的是**包自己的清单**，不是救火。这也正是它一直没被发现的原因。

**规则怎么写**（用语法树，跟 `check:user-facing` 同一套）：

- 静态 `import ... from 'x'` / `export ... from 'x'` ⇒ **必须**在 `dependencies` 或 `peerDependencies` 里；
- `import type ...` / `import { type A, type B } ...` ⇒ 不算（编译后不留痕，dev 就够）；
- `try { await import('x') } catch {}` ⇒ **不算** —— 那是 ESM 里明写"这个可以没有"，本仓 `dsh-plugin`
  对 `@deepseek-ai/dsh-agent` 正是这么用的（注释："拿不到就只传 agentOptions，插件不该整个起不来"）。

**验证**（自检 17 条 + 两道真文件控制组，都用 sha 断言"确实改到了"）：

| 控制组 | 期望 | 实测 |
| --- | --- | --- |
| 抽掉 `core` 新加的那条 peer | 报出该包 | ✅ `@butler/core` |
| 把 `dsh-plugin` 那处的 try/catch 拿掉 | 报出 `@deepseek-ai/dsh-agent` | ✅ 报了（**豁免是承重的**） |
| 不再认"全是 type"的命名导入（规则内部） | 自检点名 | ✅ 那条 |
| 不再看有没有被 try 包着（规则内部） | 自检点名 | ✅ 两条 optional 用例 |

⚠️ 这一轮两次"咬到自己"都值得记：

1. **语法树比我手写的正则审计多找到一处**（`dsh-plugin` 里那个**动态** `import()`）—— 结果它是**故意
   可缺**的 ⇒ 不是仓库的错，是**我的规则太严** ⇒ 补上 try/catch 豁免。两个方向都学到了。
2. 自检漏了 `export { A }`（没有 `from`、`moduleSpecifier` 是 `undefined`）这个形状 ⇒ **真跑时崩了**
   （自检 15 条全绿也没拦住）⇒ 补成第 15 条。第 49 轮那句"自检验语义、真跑验形状"又应验一次。

**没做的**：没把那 4 个写 `dependencies` 的包也改成 peer（它们能跑，动它是另一件事）；没查
"`dependencies` 里声明了却没用到"的（**会误报**：CLI 用**字符串**装配插件，那些名字不是 import）；

**它替人走的部分**（16 项断言，每项对着手册里的一句承诺）：版本 ≥ 0.2.1 ｜ 没配置时
`doctor` 说人话 ｜ `init --im feishu` 写出通道行 ｜ **引导页印出来的探针路径真的存在**、
`--dry` 跑得通 ｜ 假凭据下 `doctor` 报出「凭据不对／应用缺权限」两种可能 + 点出
「改配置要发版」｜ 去重表那行在（M-a 的幂等靠它）｜ `run` 以 feishu 起来、`client ready`、
说清 `not_connected`、**自己带着 EXIT=1 退出来** ｜ 没停在贴 key 那步、没开那条带一次性
token 的引导页 ｜ 五份输出里**没有** `app_secret` 的值 ｜ **真 `~/.butler` 指纹一字未变**
（脚本自己核对，和本仓的绊线同一把尺子）。

**写它时踩的三个坑**（都是"看着绿其实没验"那一类，记下来省得再踩）：

1. `set -e` **会被子 shell 继承** —— 写成 `run; printf 'EXIT=%s' "$?"` 时，
   `run` 一返回 1 子 shell 就当场退了，**printf 永远不执行**，于是"退出码"永远是"没有"。
   改用 `if`（`set -e` 不拦 `if`）。
2. 重定向要罩住**整个子 shell**；只罩 `env` 那条命令的话，`EXIT=` 会漏到脚本自己的 stdout 上。
3. 反向控制第一版写的是 `BUTLER_CLI=/bin/true` —— **这台 macOS 上根本没有 `/bin/true`**，
   它红的是"找不到 CLI"，**红得不是地方**。换成真存在、什么都不打印的替身，才红在
   「版本号不像 x.y.z」—— 那才是"断言不是摆设"的判据。

**没做的**：它**不碰**要真人扫码的那一下（永远走不了，手册里也照旧写明"这一步只能人来做"）；
没在 CI 里断言输出文案的**措辞**（只断言关键短语，将来改文案不必跟着改脚本）。
**没验**：真机验收 —— 仍然卡在这里，目标继续 active。

### 第 59 轮：把单聊准入透出来 —— `dmMode` / `dmAllowlist`（README 里挂着的那条"还没做"）

README 的"它不做什么"里挂着一条：「没把单聊的准入策略透出来」—— 官方的 `dmMode` 默认
`'open'`，也就是**企业里谁都能私聊驱动机器人**。这轮把它补上（那句如实的话也跟着改了）。

**先查官方声明，不猜**（猜错就等于配了没配）：`@larksuite/channel` 0.7.1 的 `.d.mts` 写着
`dmMode?: 'open' | 'allowlist' | 'pair' | 'disabled'` —— **四个**取值，不是两个；而且
`dmAllowlist` 要的是**发送者**的 id（`ou_…` / `user_id` / `union_id`），类型注释里点名：
「别把应用 id（`cli_…`）放进来：真实的发送者永远不是 `cli_`，所以填了等于谁也没放行」
（官方 SDK 会打一句 warn，很容易被刷过去）。

**做了什么**：Config 加 `dmMode`（默认 `'open'`，和官方一致 ⇒ 不配的人行为一点不变）
和 `dmAllowlist`；两样都原样透给官方；`dmAllowlist` 空着就**不传**这个字段（和
`groupAllowlist` 一个写法）；里面有 `cli_` 条目时 `start()` **喊一声** —— 但**不替你改**，
照传（和 `groupAllowlist` 那条"只转达、不判断"的立场一致）。

⭐ **为什么 schema 用联合类型而不是 `z.string()`**：官方对**不认识的** `dmMode` 是照 `open`
处理的 —— 用户把 `allowlist` 写成 `allowList`，拿到的不是报错，而是**悄悄全放开**。
联合类型把这个错误挡在装载时，有用例钉着（六个错值全试）。

**一个真被咬到的坑**：`larkOptionsOf` 是**导出**的纯函数，`sdk-log.mjs` 会拿**裸 config**
直接调它 —— 我照着 `allowChats` 的写法写了 `config.dmAllowlist.length`，当场 TypeError。
构造函数里那段"所有默认值都在这里兜一次底"的注释救不了导出函数：**导出函数要自己兜**。
（现在有用例守着：那条精确 `deepEqual` 的用例喂的就是裸 config。）

**再补一条我自己用例的盲区**：上面全部是 `new FeishuChannel(...)`（走构造函数），而用户改的是
`config.json` —— 那条路是 **schema 在接**，只验构造函数等于**假设** schema 接住了。所以在
`cli/test/real-composition.mjs` 里又加了两条走**产品真路径**的（`boot()` + 包名寻址）：
① 写进去的 `dmMode` / `dmAllowlist` 真的到插件身上、没写的补成 `open` / `[]`；
② `dmMode` 拼错 ⇒ **装载如实报错**。这条在下面那个 M3 突变下**精确**变红。

**突变控制**（三处新守卫各改坏一次，红的必须是**对**那条）：`dmMode` 兜底拿掉 ⇒ 红的在
`sdk-log`（裸 config 那条路径）；`cli_` 警告删掉 ⇒ 红的在 `plugin`；schema 换回
`z.string()` ⇒ 红的在 `policy`。三次都逐字节还原（full sha）。

**没做的**：让 `doctor` 报告当前的 `dmMode` —— 这一条**第 60 轮就补了**（见下一节）；
`dmMode` 仍只能手改 `config.json`，没做成 `butler init` 的问询项。审批卡片、入站语音转写还在
"它不做什么"里挂着。
**没验**：真机验收 —— 仍然卡在这里，目标继续 active。

### 第 60 轮：让 `doctor` 说出「谁能私聊它」（以及一条差点假绿的守卫）

第 59 轮把 `dmMode` / `dmAllowlist` 透出来了，但配好之后**没地方确认它生效了** ——
`config.json` 里写没写对、写对之后是不是真的到了插件身上，用户只能猜。这轮补上：自检里多
一条 `飞书私聊准入`，`butler doctor` 会打出来。

**分寸**：只有**确凿配错**（名单里出现 `cli_…`）才报 ✗；`open` 是默认、`disabled` 可能是
故意关掉的 —— 把那些报成 ✗ 只会训练用户忽略自检。所以其余情况如实描述
（`dmMode=open —— 谁都能私聊它（企业里同公司的人都行）`），不吓人。

**两条出口都要报**：`check()` 有"没凭据 / 有凭据"两条 return，而这一条跟凭据无关 ——
抽成 `dmCheck()` 两边都推。有一条用例专门钉这个：只挂一条出口的话，**没凭据的新用户看不到
它**，而那正是他最可能跑 `doctor` 的时候。

⭐ **一条差点假绿的守卫**：这个文件里早有一条「凡是给了探针命令的话，家不在默认位置时
**每一处**都要带 `--home=`」的断言（第 53 轮为"这一族已踩过四次"立的）。我这轮的 fix 也给了
探针命令，但它只在 `dmAllowlist` 配错时才出现 —— 而那条守卫当时只在**名单为空**时收集，
于是我把 fix 写死成不带 `--home=` 的命令，它**照样绿**（实测过）。这正是本项目那句
「守卫的范围是假设的，本身就是沉默的洞」。做法：给它补上第 4 种收集状态（`cli_` 配错那条
路），门槛从 4 处提到 5 处 —— 补完再量，守卫实际收到 **6 处**，而写死成不带 `--home=`
立刻**精确变红**。

**用户可见端也验了**：`cli/test/doctor.mjs` 里加了一条真通道 + 真 `doctor` 的用例，断言这一行
真的出现在**打印出来的报告**里 —— "适配层的 `check()` 里有这么一条" 和 "用户看得见" 是两件事。

**没做的**：`dmMode` 仍然只能手改 `config.json`（没做成 `butler init` 的问询项 —— 默认 `open`
是合理的，"收紧"是少数人的需求）；审批卡片、入站语音转写还在"它不做什么"里挂着。
**没验**：真机验收 —— 仍卡在这里，目标继续 active。

### 第 61 轮：把「谁能私聊它」也放进离线演练（`rehearse:feishu` 16 → 20 项）

第 59/60 轮往手册第十二节写了 `dmMode` / `dmAllowlist` 那一段，还承诺了三句话：
默认是 `open` 且等于"企业里谁都能私聊它"、填成应用 id 等于没放行、`dmMode` 写错会在
**装载时**报错。⭐ 可是**离线演练一个字都没提它** —— 而演练的全部意义就是"除了扫码那一步，
其余每一步都在本机按手册走一遍"。这轮把那四句承诺都变成断言。

**演练真的去改 `config.json`**（照手册教用户的动作：往通道配置里插两行），然后四次 `doctor`：
① 不写这两个字段 ⇒ 如实报 `dmMode=open` 并说清含义（**但不报 ✗** —— 默认不是错误，报成 ✗
只会训练用户忽略自检）；② 填 `ou_…` ⇒ 报 ✓ 且说清"名单 1 条"，**不许误报 ✗**；
③ 填 `cli_…` ⇒ 报 ✗ 且指到 `senderId`；④ 写错成 `allowList` ⇒ **装载时就报错**。

⭐ **一个真被咬到两次的坑**（也是手册里现在专门提醒用户的那个）：补丁是往 JSON 里插键，
而 `"appSecret": ""` 是通道配置里**最后一个键**、后面本来没有逗号 —— 插进去之后
`"appSecret"` 和 `"dmMode"` 之间就缺一个逗号，整个 `config.json` 当场不是 JSON。修好逗号之后
**又**多了个尾逗号（`dmAllowlist` 成了新的最后一个键）。两次报出来的都是
「不是合法的 JSON」—— 看着像产品坏了，其实是**补丁自己**的 bug。
所以补丁现在**自证一笔**：每打一次补丁就 `JSON.parse` 一遍，不合法就在补丁那里红，
不许往下赖。手册里也加了"别忘了给 `appSecret` 那行补逗号"的提醒。

⭐⭐ **突变控制抓到我自己的一个假断言**：④ 原来写的是 `grep -q 'dmMode'` —— 把 schema 换回
`z.string()`（也就是让拼错的取值被接受）之后，自检会照常打出 `dmMode=allowList`，
**这条 grep 就被那个"邻字符串"满足了**，整个演练**照样绿**。这正是那句
「一个被邻字符串满足的断言不是守卫」。改成两头钉死：① 必须看到**枚举校验**那句
（`but got "allowList"`）；② 不许出现任何 `dmMode=`（出现了就说明它被接受了）。
（同一轮还发现第一次的①突变我只删了两条出口中的一条，所以"去掉了自检"是假的 ——
不完整的突变和不做突变一样没有意义。）

**突变控制**（四处各改坏一次，红的必须是**对**那句）：去掉自检 ⇒ 「doctor 没报「飞书私聊准入」
这一条」；去掉"名单 N 条" ⇒ 「没说清名单里有几条」；不去识别 `cli_` ⇒ 「`cli_` 那条错配没被
报出来」；schema 换回 `z.string()` ⇒ 「拼错的 `dmMode` 没在装载时报错」。四次都逐字节还原。

**没做的**：没把演练扩到"重启管家才生效"那半句（那要真起进程，已有的那步是拿假凭据起的，
不覆盖这一族）；审批卡片、入站语音转写还在"它不做什么"里。
**没验**：真机验收 —— 仍卡在这里，目标继续 active。

### 第 62 轮：验一句手册里的承诺 —— 「改完要重启管家才生效」

手册第十二节那句 `dmMode` 段落的结尾写着「改完要重启管家才生效」。⭐ 这句话是**对用户的承诺**，
而且**可离线验**，所以验一遍 —— 两头都要，少一头都不算验过：

- ① 已经起来的那个实例**不会**自己变（配置是装载时读的，没有热重载）；
- ② 重新装载就变了 —— 那才是"重启"在这个项目里的含义。

`cli/test/real-composition.mjs` 里加了这条：起一份 → 确认是默认 `open` → **改文件** → 等 300ms
再读**同一个实例**（必须还是 `open`）→ 再起一份（必须变成 `allowlist`）。
钉住它的理由写在用例里：这是对用户的承诺，哪天有人加上热重载，这里会红，手册那句话也就该改了。

⭐ **突变控制里学到一件事**：我先想用"把构造函数里的 `?? 'open'` 改成 `?? 'disabled'`"当控制，
结果它**永远绿** —— 因为 `boot()` 会先过 **schema**，缺字段时 schema 已经把值补成 `'open'` 了，
构造函数那层兜底在 `boot` 这条路上**根本走不到**。它只为"**直接 `new`**"而存在，而那条路由
`policy.mjs` 的 `real({})` 钉着。所以这条新用例唯一有效的控制是**改 schema**
（`z.union(…)` → `z.const('open')`，让写进去的值被忽略）—— 那样它会红，而且精确红在
「改 config.json 里的 dmMode 要重启才生效」和「dmMode / dmAllowlist 真的落到插件身上」这两条上。

（顺带一个纯粹的绊脚：**`lib/` 的缩进不是 `src/` 的缩进**（同一处是 12 个空格 vs 6 个），
按 `src/` 的样子去 lib 里改锚点会"锚点没命中"。）

**没做的**：没验「热重载」本身（项目里压根没有，所以这是"验了没有"，不是"验了有"）；
没验真机上"重启"的完整动作（`butler run` 起/停那一组已有专门用例）；审批卡片、入站语音转写
还在"它不做什么"里。
**没验**：真机验收 —— 仍卡在这里，目标继续 active。

### 第 63 轮：让「演练 20 项 ✅」这句话本身也被人盯着（`mutate` 收编 `scripts/`）

deferred 里挂着一句「`mutate` 不覆盖 `scripts/`」。⚠️ 但按 `mutate` 的语义（**改坏产品** →
看有没有**测试**喊疼），`scripts/` 不该当**受害者** —— 它们就是测试，拿测试当受害者等于
"把体温计砸了看它准不准"。真正的意思是：把 `scripts/` 当**喊疼的那一方**，也就是把第 61 轮
我**手工**做过一次的那种突变控制，变成常设的。于是 `mutate.mjs` 的 `e2e` 字段现在可以**写脚本路径**
（`e2e: true` 仍是历史那条 clean-room 脚本），并加了四条 witness 指向 **飞书手册的离线演练** ——
每条各打掉演练里的一条断言：① 默认那条 `open` 不再报出来；② 报 allowlist 时不再说名单几条；
③ 填成应用 id 不再吭声；④ `dmMode` 写错在装载时不再报错。结果是 **4 处见血 / 0 处没被盯住**，
而且每条红在**对的那句**（「没报这一条」/「没说清几条」/「`cli_` 没被报出来」/「没在装载时报错」）。

⭐⭐ **顺手补掉一个真洞**：`e2e` 这条分支原来**不重编**。对 `install.sh`（历史上唯一的 e2e 目标，
shell，本来就不用编译）是无害的；但变异点一旦落在 **`.ts`** 上，副本里的 `lib/` 还是**原代码** ——
于是"红了 / 还是绿的"这个裁决是关于"什么都没发生"的。**控制**：把这句重编拆掉再跑，四条**全部**
变成「★ 还是绿的 / 4 处没被任何测试盯住」。也就是说，不补这一句，这个功能上线就会**凭空指控
演练没盯住这四条**（而那四条明明在）—— 一个静默的假警报。

⭐ **两条被 `mutate` 自己抓出来的东西**（正好说明它值这个钱）：
- 我第一条突变的锚点选的是 `ok: false` 那处的 `name`，可**默认（open）走的是 `ok: true` 那条
  return**，字符串还在别处 ⇒ doctor 照样打出来 ⇒ 这条突变**没牙**，跑出来是「★ 还是绿的」。
  锚点换成默认那条路之后才见血。
- `pnpm mutate --only 飞书私聊准入 --quick` 报的是「**--only 没匹配上任何一处**」—— 那是**假话**：
  它匹配上了 4 处，只是那 4 处**全是 e2e**、又被 `--quick` 滤掉了。我照着这句话去查 Unicode
  规范化（怀疑 macOS 的 NFD），白花三轮才看穿它。**把人引到错地方的错误信息比没有更坏**，
  所以那句话改成了分别说清两种原因（附实测：改后它说的是「匹配上了 4 处，但它们全是 e2e，
  被 --quick 滤掉了」）。

⭐ 全量跑完还顺手清了一笔**旧账**：清单里 `--again：跳过时不再把旧 token 注入回去` 这条的锚点
**早就漂了**（`onboarding.ts` 后来重构过形状，清单没跟上），所以它一直报「不算数」——
而 `mutate` 的退出码在有"不算数"时也是非 0，等于**这支工具会永远红着**，久了就没人看它的退出码了。
把锚点按源码现状刷新（意图不变：跳过时不许把旧值注入回去）之后，它红了，而且红在**完全对上**的
那条用例上（「`--again` 换 token 但跳过：原来那串必须还在行里」）。至此全量是
**70 处砸了、70 处见血、0 处没被任何测试盯住、0 处不算数**。

**没做的**：没给 `e2e` 支持"多条脚本"或"自定义判红正则"（现在判红固定看 `❌` 行或非零退出，
`install.sh` 那条和演练这条都够用）；没把 `mutate` 挂进 CI（跑一遍几十分钟，它一直是手动工具）。
✅ **（第 68 轮补）** 现在它**按周**自动跑一遍（`.github/workflows/mutate.yml`，周日 03:17 UTC）。
仍然**不进**每次 push 的那套 CI，但⚠️**理由要更正**：这里写的"跑一遍几十分钟"是**估的、而且是错的** ——
第 68 轮在 ubuntu runner 上实测 **7 分 48 秒**，而普通 CI（三个 Node 版本的矩阵）约 **2 分钟**，
只差 4 倍。真实理由见那个工作流开头的注释：① 矩阵里放进去等于**白跑 3 遍**（变异结论与 Node
版本无关）；② 它测的"**断言还咬不咬得住**"是**周**级别的性质，不必卡在每条提交的必经之路上。

  本来就该能用它；

  取漏了比"仓库里真有违规"危险得多，因为它是静默的）。

> ℹ️ 说的是**运行期**，不是源码里的行号顺序。第 66 轮量过：探针源码里这 5 句的行号是

> **单聊里不用 @ 它**（群里才要）—— `requireMention` 只管群聊，这是读了官方实现确认的

1. 一个二维码（或一条链接）+ 几行 `扫码状态：…`
2. `拿到凭据了（不打印内容）`
3. `长连接已建立。机器人身份：<名字>（<open_id>）`
4. 你发一条消息之后：一段 `收到一条消息：{…}` 的**真实字段** JSON，紧接着 `已回复（om_…）`
5. 探针通了之后：`Ctrl-C` 掉 → **`butler init --im feishu`** → 再 `butler run`；**然后你自己先发第一条消息**（见下）

> ⚠️ **`butler run` 会先问你一两件事 —— 那不是出错**（两件都**不用改任何文件**，也不用去后台）：
>
> - **飞书应用的 app_id / app_secret**：扫码那条路（`--save`）存过的话，它会直接说
>   `通道凭据：填上了你上次存的那串 ✓` 并跳过；没存过就在**本地页面**里等你粘贴 —— 把终端里那个
>   `http://127.0.0.1:…` 地址复制到浏览器就行（**开二维码的是探针**，它不开二维码）。
> - **模型 key**：`模型 key：还没有，起了一个本地页面让你贴` —— 就在那儿贴（也可以先跳过，
>   下次 `butler run` 会再问）。
>
> 两件都齐了才轮到"上线"：插件那棵树打完，**连不上**才会停在 `起不来：…`（见下面那张表）。
> 顺序是**通道凭据 → 模型 key → 上线** —— 第十一节第 28 轮记过为什么是这个顺序。

> ⚠️ **中间那步不能省**：`--im` 是 **`init`** 的选项（`butler run` 没有这个选项）。这一台原来收的是
> 微信/Telegram 的话，不切过去，跑起来收信的**还是原来那个通道** —— 凭据存着也用不上，你在飞书里
> 发消息**什么都不会发生**。（第 23 轮之前更糟：`init --im feishu` 在**已有**配置上什么都不改，
> 那个通道行永远换不过来。现在它会**原位换那一行**并告诉你换成了什么。）
>
> **从第 44 轮起，忘了也不会再"什么都不会发生"**：管家自己看得出来 —— 盘上凭据齐了、配置里却没有这条
> 通道时，`butler doctor` 的装载段和 `butler run` 的"读配置"之后都会印一句
> `盘上已经有飞书的凭据，配置里却没有那一条通道 —— 跑一次 butler init --im feishu 把它接上（凭据不用重扫）。`
> （实现见第十一节第 44 轮。）

> ⚠️ **第一条消息必须你自己发。** 内核的认主不是配置项，而是**第一条来信**：默认没认主时，
> **第一个来消息的人就成了这台机器的主人**（之后能遥控它跑命令），别人发消息它会**一声不吭**。
> 而飞书这边 `dmMode` 默认是 `open` —— **同一个企业里谁都能单聊这个机器人**。
> 在公司租户里别只是"把它跑起来"就放着：你先发一条，把它认下来。
>
> 想彻底钉死（比如给同事用的机器）：探针打印的 JSON 里有 `senderId`，把它写进
> `<管家目录>/state/state.json` 的 `owner`，再起管家 —— 那就不会再有"谁先说话谁当家"这回事。
> 认主的结果也在那个字段里：`doctor` 里那条 **`谁能指挥它`** 会说清 —— 已认主时**连是谁一起写**
> （`已认主（第一个跟它说话的人）：ou_…。别人发消息它会一声不吭`），还没认主时写
> `还没认主 —— 第一个给它发消息的人就是主人`。
>
> ⚠️ **那个文件不存在怎么办**：新装的配置（`butler init` 写出来的）里，内核那一行带着
> `stateFile`，所以**第一次认主之后它就有了** —— 先发一条消息认主，再回来看这个字段。
> **装得早的机器**当初没有这个字段（认主只在内存里，重启就忘，谁先说话谁又当家）：
> 跑一次 `butler init` 就会补上 —— `butler doctor` 和 `butler run` 都会明说这件事。
> 补完再按上面那句钉死。
>
> **还有一层：谁能私聊它。** 上面钉的是"谁是主人"，但飞书那边还有一道**更靠前**的闸门：
> 官方的 `dmMode` 默认是 `open` —— 企业里**谁都能私聊驱动机器人**（认主只决定"谁是主人"，
> 不决定"谁能跟它说话"）。要让**只有某人**能私聊（第 59 轮起可以了），把探针那段 JSON 里的
> `senderId` 抄下来，写进 `config.json` 那条通道的 `config` 下：
>
> `{ "dmMode": "allowlist", "dmAllowlist": ["ou_从探针那段JSON里抄的senderId"] }`
>
> ⚠️ **手改 JSON 时最容易少的东西是逗号**：`"appSecret": ""` 那行在通道配置里是**最后一个键**，
> 它后面原本没有逗号 —— 在它后面插东西就得先给那行补一个逗号。忘了的话 `butler doctor` 只会说
> 「不是合法的 JSON」，看不出是哪儿少的（这个坑是第 61 轮写演练脚本时自己踩出来的，见下一节）。
>
> 这一段在源码树里也有**离线演练**：`pnpm rehearse:feishu` 会真去改一次 `config.json`，
> 然后断言 `doctor` 报的行对得上（默认 / 配对了 / 填成 `cli_` / 写错取值，四种都验）。
>
> ⚠️ 填的是**发送者** id（`ou_…` / `user_id` / `union_id`），**别填应用 id**（`cli_…`）——
> 官方要的是发送者，填 `cli_` 等于谁也没放行（`start()` 会替你喊一声，但**不替你改**，照传）。
> `dmMode` 写错（比如 `allowList`）会在**装载时**直接报错，不会悄悄按 `open` 放行。
> 四个取值：`open`（默认，谁都行）/ `allowlist`（名单里才行）/ `pair`（只理配对的）/
> `disabled`（谁也不理，等于关掉私聊）。改完要重启管家才生效。
>
> 配完怎么确认真的生效了：`butler doctor` 里会有一条 **`飞书私聊准入`**，把当前取值和它的
> 实际含义打出来（比如 `dmMode=allowlist —— 只有名单里的人能私聊它（名单 1 条）`）。
> 如果名单里填成了应用 id（`cli_…`），这一条会报 **✗** 并说明"等于没放行"、该去哪儿抄真正的
> `senderId` —— 不用自己去猜有没有配错。

| `doctor` 里飞书报 `failed to get tenant_access_token, code: 10003, msg: invalid param` | 凭据**填了但不对**（手抄时少了字符最常见） | 重扫最省事 —— 但**别照抄源码树那种写法**：`doctor` 那句 fix 里就印着能直接抄的**完整命令**（包内路径；家不在默认位置时它还带 `--home=`）。`10003` = 参数无效（**▣实测**，见第十一节第 53 轮） |
| 连上了，但发消息**毫无反应** | 订阅方式不是长连接 / 没订「接收消息 v2.0」/ 权限改完没发版 | 按第四节那六步对一遍；**改动必须发新版才生效** |
| 它**只对别人有反应、对你一声不吭**（日志里出现 `忽略不属于主人的来信 from=…`） | 认主已经发生过了：空 `owner` 时"第一个来消息的人"成了主人 —— 企业里很可能是同事先发的 | 那个字段在 `<管家目录>/state/state.json` 的 `owner`；⚠️ **文件不在就先跑一次 `butler init`**（装得早的配置缺 `stateFile`，认主从来没落过盘 —— 见上面第 5 步那段） |
| 探针通了，可管家一起就说"消息偶尔不回" | 探针还挂着：同一应用**两条长连接**，飞书把事件**分流**给其中一条 | `Ctrl-C` 掉探针（探针自己在连上之前也会警告这一句） |
| 保存长连接配置时一直失败 | 官方原文：**保存时长连接客户端必须已经在线** ✓官方（见第四节"最容易卡的三处"第 2 条），顺序反了就一直失败 | 先把探针跑起来连上，再去后台保存 |
| 收到了，但回复失败 | 缺发消息的权限 | 看那行错误。⚠️ 若错误里带一条**一次性授权链接**，那是凭据，别贴给别人 |
| 附件没落进 `state/files/feishu/` | 缺读资源的权限（终端会有 `附件下载失败` 的 warn） | 加权限 → 发版 → 重试 |
| `butler run` 说"还没有 app_id / app_secret"，可你明明存过 | **存到了另一个管家目录**：凭据按"配置所在目录"找，用了 `--config` 就未必是 `~/.butler` | 给探针加 `--home=<那个目录>` 重新 `--save`（错误信息里会打印它去哪儿找过）。设了 `BUTLER_HOME` 的话：**从第 37 轮起 CLI 和探针认同一个家** —— 两边都不用再补 `--home=`/`--config`（那之前只有探针认它，别照着老版本的经验对） |
| `butler run` 起了一个本地页面，写着"飞书应用的 app_id：还没有，起了一个本地页面让你贴" | **正常**，它在等你粘贴（**会开二维码的是探针**，不是它） | 在那个页面里贴进去；或 `Ctrl-C` 掉，改跑**探针**去扫码 —— `doctor` 那句 fix 里就印着能直接抄的**完整命令**（别照抄源码树那种写法，理由见上） |
| `doctor` 说"配置里一行都没有" / "1 个插件没装上来"（而配置里明明有飞书那行） | 老代码的老毛病：凭据还没填时，官方包在**构造**就抛 `appId is needed`，插件装载失败 | 升到含"官方通道懒造"那版的代码；这一版飞书那行会**装上**，只在自检里报 ✗ |

### 探针会替你做 / 不做的

- **不 import 适配层**：只用官方包 + 一个只负责写凭据文件的 `probe/save.mjs` —— 它是一把**干净的尺子**：
  它通了而管家不通，问题一定在我们这层。⚠️ 这句话成立的**前提**是它真的一行我们的代码都没引，
  所以 `pnpm check:packages` 现在会**逐条读它的 import 语句**盯着这件事（第 67 轮）。
  判据是**语句**，不是"文件里出现过这个包名"—— `probe/*.mjs` 的 JSDoc 里本来就写着
  `@module @butler/channel-feishu/probe`，拿包名 grep 会当场误报（而"会误报的守卫比没有守卫更糟"）。
  `../` 开头的相对路径也算：它绕过包名、直接够到文件系统，一样能毁掉这条推理。
- 它**不验附件**（附件是我们这层的活）：那一步要用 `butler init --im feishu` 切过来、再 `butler run`，
  然后发一张图片，看终端有没有说落到了 `~/.butler/state/files/feishu/`
- 失败时它**不会把 `context` 打出来**：权限类失败的那个 `consoleUrl` 是签了名的
  一次性授权链接（官方类型声明里写明"是凭据，别写进日志 / 工单 / 聊天"）
- `butler doctor` 现在也能验凭据（一次免费的 REST 调用 `getAppInfo`，**不用连长连接**）；
  被拒时它只报 code/message 并摆出两种可能 —— 因为"被拒"不等于"凭据错"
