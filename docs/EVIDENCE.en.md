## Why that pile of checks exists

**The tests are deliberately built to run offline**: the WeChat media part forges its own CDN
ciphertext and runs its own AES decryption to verify things, so it needs no real account and
sends messages to nobody. CI runs the full suite on Node 20 / 22 / 24.

> One `check:docs` rule specifically hunts for 「**references to gitignored files**」 —
> everything looks fine locally, then you push to GitHub and the image is broken.
> Skip that check and you will miss this class of bug, every time.
>
> ⚠️ **(added round 50)** It only ever asked "does this file exist in the repo" — enough for a reader
> **inside the repo**, not for the person who **receives the package**: a package README opens fine on
> GitHub, but relative links on the npm page resolve against the *package*, so `../cli`,
> `../../docs/GETTING-STARTED.md` and `test/fixtures/x.ts` are all dead links there (we measured **14**
> of them across 8 package READMEs; all now point at GitHub URLs). The same defect showed up in round 47 —
> only the reader changed: that time it was **text printed for the user**, this time it is **files we ship**.
> A second rule came with it: for a full URL pointing at **this repo**, `blob` must point at a file and
> `tree` at a directory, and the path must really exist — round 41 wrote that rule down as a sentence
> ("the address in the manual must point at a file that really is in the repo"); now something enforces it.
> ⚠️ Never hard-code "which md files are shipped": the set is derived from each `package.json`'s `files`
> (round 47 missed `.mjs`, round 49 missed heredocs — twice the scope was an assumption).
>
> `check:scripts` was **forced into existence by real incidents** too: backticks inside a double-quoted
> `step "… `butler run` …"` are **command substitution**, so the command really runs while the heading
> is being built. It hung an acceptance script for 27 minutes and got misdiagnosed for two rounds
> ("must be a quirk of backgrounding processes"). The repo has been bitten **twice** (the other one was
> in `install.sh`'s heredoc), so it is a CI check now rather than a note in a comment.
>
> ⚠️ **(added round 49)** Back then it recognised only the three names `step`/`ok`/`bad`, and it never
> looked at heredocs at all — while its own header records that the *other* bite happened in a heredoc:
> the escaped backtick on `make-installer-bundle.sh:95` could lose its backslash and nothing would say a
> word. It now **works out which functions print** from the source (any function whose body contains
> `printf`/`echo`, plus the transitive closure — `die()` contains no `printf` at all, but it calls
> `say()`), and separately scans **unquoted heredocs** for bare backticks (`<<'EOF'` does not expand, so
> it is skipped entirely). While changing it, it bit itself twice: once when a `RegExp` went into a
> template literal and the backtick closed the string early, and once when "find the function's end by a
> leading `}`" swallowed the next three functions — the second one was caught by the new **cross-check
> guard** (count `name() {` in the source vs the bodies actually extracted), which the self-test could
> *not* catch, because its synthetic cases are all single-line functions.
>
> `check:packages` was **forced into existence by a real incident**: listing file names one by one
> in `files`, missing one build artifact, and the symptom is "it installs, but it will not start"
> (`Cannot find module '…/lib/sessions.js'`) — the repo looks perfectly fine, because the source is
> right there. The rule now is **ship whole directories**, and this script enforces it.
>
> ⚠️ **(added round 51)** It only ever asked "did the files come along", never "are the dependencies
> declared correctly" — the other half of the same root cause, and the sneakier half: a missing artifact
> in `files` fails **immediately** with `Cannot find module`, while a dependency that lives only in
> `devDependencies` works forever locally (the repo has it installed, the host happens to declare it too)
> and only explodes on another machine or when someone uses the package directly. We measured **7
> packages** that import `@deepseek-ai/schemastery` as a **value** at runtime while declaring it only in
> `devDependencies` — even though the same packages declare `@deepseek-ai/cordis` (equally host-provided)
> as a `peerDependency`. Host-provided things belong in peer, and then the manifest tells the truth. The
> rule uses a syntax tree to tell a value import from `import type` (types leave no trace, dev is fine),
> and it deliberately **does not** count `try { await import('x') } catch {}` — that is how ESM says "this
> one is optional", which is exactly what this repo's `dsh-plugin` does with `@deepseek-ai/dsh-agent`.
> ⚠️ To be clear: the installed system **was already fine** (the CLI declares schemastery as a
> `dependency`); what got fixed is the **packages' own manifests**, not a fire.
>
> `check:user-facing` was **forced into existence by the third occurrence of the same sentence**: the
> installed machine has no `packages/`, `docs/` or `scripts/`, and hints pointed at those paths three
> times (round 40's probe path, round 41's manual address, round 43's in-package path). It uses **a
> syntax tree, not a regex** — comments are full of `docs/…`, and `//` also appears inside
> `https://…`, so a regex that strips comments is guaranteed to get it wrong. Its scope is not
> "which directory" but "**who is reading this line**": `packages/*/src`, `packages/*/probe` and
> `install.sh` are checked, `scripts/*.sh` is not (maintainer tools — whoever runs them has the repo,
> which is exactly where all 5 first-run hits lived). So what it caught on its first day was not a
> violation, but a **boundary**.
>
> `mutate` asks a different question: **is "the suite is green" actually green?** It deliberately
> breaks every promise and checks whether any test cries out — the ones that don't cry out are
> promises that only hold in the docs. It is **deliberately kept out of CI** (ten-odd minutes, and
> it rebuilds over and over inside a copy): it is what you run when you want to verify **the tests
> themselves**. The first version used `cp -al` hard links as the copy, so writing a file truncated
> the same inode and mutations **leaked back into the original repo** — so now the copy must be a
> real copy (compared file by file via inode), and the original repo has a hash tripwire watching it.
