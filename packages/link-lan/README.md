# @butler/link-lan

`ctx.link` 的第一个真实现：**局域网链路**。两台电脑连同一个 WiFi，就能让管家去够到第二台。

零依赖：只用 `node:http` + 内置的 `fetch`。不用装 Tailscale、不用开端口映射、不用注册任何账号。

## 它给了两半

| 跑在哪 | 装哪个入口 | 是什么 | 干什么 |
| --- | --- | --- | --- |
| **中枢**（你平时用微信的那台） | `@butler/link-lan` | `LanLink` | 一个 cordis 插件，注册成 `ctx.link`。负责发现设备、连过去 |
| **节点**（被遥控的那台） | `@butler/link-lan/node` | `NodeService` | 注册成 `ctx.node`。开端口听请求，把活转给**本机的 agent** |

一个包两个入口，跟 `wechat-agent-bridge` 是同一手法（`exports` 子路径，不是拆包）。
两半共用线协议；分入口的理由不只是"干净"：节点那半依赖 `@butler/seam-agent`（要驱动本机 agent），
中枢那半不需要。

底下还有两个不走插件的类：`LanNode`（HTTP 服务端）和 `LanSession`（会话客户端）。
`NodeService` / `LanLink` 分别是把它们接进 cordis 的那一层。

**别的链路实现会复用这个包。** `@butler/link-tailscale`（跨网那条）
线上跑的就是这里的 HTTP + SSE —— 它直接用 `LanSession` 和 `pingNode`，
自己只负责"怎么找到那台机器"。这不是凑合：**同一个 seam 的两个实现，
该分叉的是发现，不该分叉的是线上协议**。哪天真出现第三种传输，
再把线协议抽成 `@butler/link-wire` 也不迟。

## 配置

**最省事的那份配置：什么都不用写。**

```jsonc
{ "link": { "lan": { } } }
```

设备是用**配对**收进来的（见下一节）：那台电脑上跑 `butler node`，它会在屏幕上打出一行
「配对 192.168.1.9:41338 4A7-K2M」，把这一行发到微信里就收下了。收下的设备记在
`~/.butler/peers.json`（权限 0600），**中枢重启还记得**，不用重配。

手写也仍然支持（比如你想一次配好、不想配对）：

```jsonc
{
  "link": {
    "lan": {
      // 手写的设备必须有个密钥来源：要么它们各自带一把，要么这里给一把共享的
      "secret": "openssl rand -hex 16 的输出",

      // 你有哪些电脑。alias 就是你在微信里叫它的名字
      "peers": [
        { "id": "node-home",  "alias": "家里那台", "host": "192.168.1.9",  "port": 41338 },
        { "id": "node-study", "alias": "书房那台", "host": "192.168.1.12", "port": 41338 }
      ],

      "peersFile": "",           // 配对收下的设备记在哪。空 = ~/.butler/peers.json
      "idleTimeoutMs": 120000,   // 多久没动静算掉线（是"空闲"不是"总时长"）
      "pingTimeoutMs": 800,      // 探活一次最多等多久
      "pairTimeoutMs": 5000      // 配对那一次最多等多久
    }
  }
}
```

手写的一台也可以自带密钥：`{ "id": "…", "alias": "…", "host": "…", "secret": "…" }`。

`id` 一旦定下就**别改** —— 用户的「以后都放那台电脑上」指的是它。

## 配对：怎么把第二台电脑交给管家（✅ 已实现）

**用户要做的只有一件事：把屏幕上那一行发到微信里。**

```
（在那台电脑上）$ butler node --config node.json

节点「家里那台」上线了。
  监听：0.0.0.0:41338

  把这台电脑交给管家 —— 在收微信的那台机器上，用微信发下面这一行
  （可以复制，别手打）：

      配对 192.168.1.9:41338 4A7-K2M

  配对码 4A7-K2M 只能用一次，30 分钟后作废。
```

那台电脑**配置里不写 id、不写密钥**：它第一次上岗时自己生成一份，存在
`~/.butler/node.json`（权限 0600），之后一直是同一个身份。

### 密钥是谁的

|  | 初稿 | 现在 |
| --- | --- | --- |
| 密钥谁生成 | 用户，两台机器各抄一份 | **节点自己** |
| 密钥怎么到中枢 | 用户手抄 | 配对时**从节点换回来**，只走局域网 |
| 一台泄漏影响几台 | 全部（共用一把） | 只有那一台 |

配对码**走微信**（用户是从另一台电脑的屏幕上抄过来的，中间经过腾讯的服务器），
所以它**只能用一次、错 5 次作废、30 分钟过期**。它换回来的长期密钥
**只在这一条局域网链路上**走 —— 微信自始至终没看见它。

### 那个请求凭什么能进来

配对是唯一一个"还没有密钥也能进来"的请求，但**认证的红线没破**：

| 请求 | 凭据 | 什么时候判断 |
| --- | --- | --- |
| 平时的调用 | `Authorization: Bearer <密钥>` | 读第一个字节**之前** |
| 配对 | `x-butler-pair: <配对码>` | 读第一个字节**之前** |

凭据换了，顺序没换。

### 中枢可以在微信里管这些

| 你说 | 它做什么 |
| --- | --- |
| `配对 192.168.1.9:41338 4A7-K2M` | 收下那台电脑（**密钥只在这条局域网上走**） |
| `设备` | 现在认识哪些电脑、在不在线、最后在线多久前 |
| `忘掉 家里那台` | 不再管那台电脑（写在配置文件里的那台忘不掉，会告诉你去哪删） |

忘掉之后名册文件里也删掉，不留半条。

## 节点侧怎么跑

被遥控的那台电脑上写一份**自己的**配置（注意：没有 channel，也没有 core）：

```jsonc
{
  "plugins": [
    { "id": "agent", "name": "@butler/agent-dsh", "config": { } },
    { "id": "node",  "name": "@butler/link-lan/node",
      "config": {
        "alias": "家里那台",      // 你在微信里叫它的名字
        "port": 41338,
        "cwd": "/Users/你/要它管的目录"
        // 没有 id、没有 secret —— 它第一次上岗时自己生成，存在 ~/.butler/node.json
      } }
  ]
}
```

然后：

```bash
butler node --config ~/.butler/node.json
```

```
装载：
  ✓  agent  @butler/agent-dsh
  ✓  node   @butler/link-lan/node

节点「家里那台」上线了。
  监听：0.0.0.0:41338

  把这台电脑交给管家 —— 在收微信的那台机器上，用微信发下面这一行
  （可以复制，别手打）：

      配对 192.168.1.9:41338 4A7-K2M

  配对码 4A7-K2M 只能用一次，30 分钟后作废。
  过期或者抄错了，重起这个命令就会换一个新的。
（Ctrl-C 下线）
```

**用户唯一要做的事就是最后那一行**（配对那一节讲它到底是怎么安全的）。

**`ctx.node` 不是五个 seam 之一** —— 它跟 `ctx.core` 一个性质：某个具体插件自己的槽位。
做成服务位是为了让 `butler node` 能像 `run` 调 `core.start()` 一样对称地写，
并且能拿到真实的监听端口打给用户看。

`static inject = ['agent']` 白拿了门控：**一台没装 agent 的机器上，这个服务根本不会被构造**。
不需要自己写"没有 agent 就报错"，也不会出现"节点在线但没人干活"这种最让人困惑的状态。

### 一道刻意的安全闸

配置里只要有通道，`butler node` 就**拒绝启动**：

```
这份配置里有通道 —— 节点不该登录任何 IM。
同一个账号被两个进程同时收信，消息会随机分到两边，看起来就是"时好时坏"。
```

这不是洁癖。同一个 IM 账号被两个进程同时长轮询，消息会**随机**落到其中一边，
而两边日志都正常 —— 用户看到的是"有时回有时不回"，极难查。宁可拒绝启动。

## 远端产出的文件怎么回来：铸取件凭证（✅ 已实现）

节点上的 agent 可能产出一个文件（报表、截图）。难点只有一句话：
**那个路径在中枢那台机器上不存在。**

所以这里**绝不透传路径**，而是给每个文件铸一张**取件凭证**：

```
节点上 agent 返回  files: [{ path: '/home/leo/报表.xlsx', name: '报表.xlsx' }]
        ↓ 只在自己内存里记下 token → path
回给中枢           files: [{ token: 'a3f…', name: '报表.xlsx' }]
        ↓ 中枢拿 token 调 file.read，按 512 KiB 分块取
```

这么做换来的是一条**结构上就成立**的保证：**中枢只能拿到 agent 主动交出来的那些文件**，
拿不到这台机器上的任意路径。就算中枢那台被攻破、密钥泄漏，它也没法把这里当成
"读取任意文件"的接口 —— 它**压根没有路径可填**。

| 方法 | 干什么 |
| --- | --- |
| `file.read` | `{ token, offset }` → `{ name, caption, size, offset, eof, data }`（`data` 是 base64 的块） |
| `file.drop` | `{ token }` → 取完就还，不留着 |

几条落在实现里的规矩：

- **凭证十分钟不用就作废。** 用户说"发我那个报表"，agent 早就跑完了；
  十分钟后还来取，只可能是有人在瞎试。不认识的凭证和过期的凭证回**同一句**话
  （免得这个接口变成探测工具）。
- **大文件分块取**，不是一口气读进内存 —— agent 会产出多大东西谁也不知道。
  分块还顺手换来一个好处：中枢可以播报"正在取回 报表.xlsx（63%）"，用户不会以为卡死了。
- **文件其实不在了**（被移走、没权限）→ 说清楚是**哪一个**、为什么。
  文件名的前半段就是展示名，中枢可以原话转给用户。

## 安全边界（请认真看这段）

**局域网是共享介质。** 同一个咖啡馆 WiFi 上，任何人都在同一个广播域里，扫一下就能看到这个端口。

所以：

- **节点侧永远有一把密钥**：配置里不写就自己生成，绝不会"不设防地起来"。
  中枢侧**可以一把都不配**（设备是配对收上来的，各自带一把）；但**手写在配置里的设备**
  如果没有密钥来源，插件会直接抛错 —— 那种配置连上去只会得到一个 401，
  用户从现象里看不出为什么；
- 认证在**读第一个字节之前**完成 —— 不做流式鉴权，那样未授权的请求已经能把数据写进来了；
- 密钥比较用 `crypto.timingSafeEqual`，不是 `===`。`===` 在第一个不同的字符上就返回，逐字节试就能把密钥试出来，而局域网里攻击者离得很近；
- 自检里有一条会专门为短密钥报警（低于 12 位）。

别把 `secret` 设成 `"123"`。

## 线协议

一次调用 = 一次 HTTP POST，响应是 SSE 流：

```
POST /butler/call
authorization: Bearer <secret>

{"method":"agent.run","params":{...},"protocol":"butler-lan/1"}
```

```
data: {"type":"progress","line":"正在打开那个文件夹"}
data: {"type":"done","result":{"text":"整理好了"}}
```

失败时最后一帧是 `{"type":"error","message":"...","code":"..."}`。

**为什么是 SSE 不是 WebSocket**：Node 内置了 WebSocket 客户端但**没有服务端**，服务端要第三方库。这个项目的原则是能不加依赖就不加，而一次调用的方向本来就单一（一问 + 一串进度 + 一个结果）。

## 几个刻意的选择

**超时按"空闲"算，不按"总时长"。** 远程跑一次 agent 可能就是几分钟，按总时长掐会把正常的长任务误杀。只看"多久没动静了"—— 对面还在报进度就说明它活着。测试里有一条专门盯这个：4 次进度、总时长超过空闲超时，照样跑完。

**`discover()` 会探活，但有时限。** 每台节点一个 `pingTimeoutMs` 的握手，**并行**发。所以关机的那台不会让整个发现卡住。连不上的节点照样出现在结果里（`online: false`），因为用户问的是"我有几台"，不是"哪几台开着"。

**`connect()` 先验活再复用缓存。** 一开始我把缓存放在验活前面（省一次往返），结果节点已经关机时 `connect` 会高高兴兴返回一个死会话 —— 失败要拖到第一次 `request()` 才暴露。这违背了「连不上要当场抛」这条承诺，是测试抓出来的。

**`check()` 不去 ping 节点。** doctor 要回答的是"配置错了吗"，不是"你开电脑了吗"。节点关机是后者。所以自检只报配置本身，跑起来是微秒级。

**`stop()` 先收掉挂着的响应再关监听。** 否则 in-flight 的 SSE 会让 `server.close()` 一直等，测试直接挂住。

## 开发

```bash
pnpm --filter @butler/link-lan test
```

65 个测试，全部离线、全部跑在 `127.0.0.1` 上，端口一律 `0`（系统分配），并行跑不撞。
分成三块：33 个在线协议与认证上（`test/lan.mjs`），19 个在节点侧（`test/node.mjs`），
13 个在配对上（`test/pair.mjs`）。

节点侧那 19 个：门控、身份（自己生成、上岗才落盘、id 不许悄悄改）、端到端、取消、
端口真的放掉，以及取件凭证那一整套（分块取回、用完就还、过期作废、文件不在了怎么说）。

配对那 13 个两头都跑真的：码对/码错/已用过/试错 5 次作废/过期/够不着，
收下之后落盘（0600）、**换个进程起来名册还在**、忘掉之后文件里也删掉，
以及"带着密钥也走不到配对那条路"（配对只能靠配对码）。
另有 7 个在 `cli` 包里（`test/node-cli.mjs`）：**真 spawn 一个 `butler node` 进程**，
中枢连过去，进度真的跨进程回来，最后 SIGINT 退得体面。
