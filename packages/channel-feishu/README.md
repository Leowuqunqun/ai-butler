# @butler/channel-feishu

`ctx.channel` 的第三个实现：**飞书 / Lark**。

## 一句话

站在官方 [`@larksuite/channel`](https://www.npmjs.com/package/@larksuite/channel) 上，**只写映射**。
长连接、断线重连、心跳、事件归一化、去重、按 chat 串行、流式卡片、媒体上传、
扫码建应用 —— 那些都在官方包里，由它的维护者管（和官方 `node-sdk` 是同一批
ByteDance 账号，飞书改协议他们先知道）。我们只做它不做的那件事：**把它折成
`ctx.channel` 认的 5 个方法**。

判断标准很简单：**这个包里任何一行跟飞书协议细节有关的代码都算 bug** ——
纯映射进 `src/map.ts`（能离线测），跨重启的状态进 `src/seen.ts`，网络全交给官方包。

## 它做什么（M-a + M-b）

- **收文本**，包括群里的 @ —— `@_user_1` 这类占位符官方包已经换成人名了，我们原样透传。
  而且**不只认文本**：官方把飞书**每种消息类型**都渲染成人能读的东西（富文本拍平、
  卡片抠字、合并转发展开整段聊天记录、群名片 / 联系人 / 位置 / 系统消息……），我们按
  **载体**分：附件承载的（图 / 文件 / 语音 / 视频 / 表情）走落盘，其余类型的渲染结果原样带上
  —— 不然那条消息对大脑就是**空的**（用户看得见自己发了东西，管家却什么都没收到）
  （**群里要 @ 它，单聊不用**：官方的 `requireMention` 只写在 `evaluateGroup` 里，
  这一点是读了官方实现确认的，`test/policy.mjs` 钉着）
- **回消息走原生引用回复**（`reply`），并把**被引用的那句原文**取回来当上下文。
  引用**回不了就退回直接发送**（你把自己那条消息删了、消息太旧、话题对不上时，官方的 `reply`
  会失败）—— 答案是刚算出来的，少一段引用好过什么都不回；**两条路都失败才往上抛**
- **按 `messageId` 去重，且跨重启** —— 飞书是"至少一次"投递，重推最远 6 小时后才到，
  那时内存去重早空了（`safety.dedup` 只管进程内，落盘表管进程外）
- **机器人发的消息一律不理** —— 群里两个机器人互相 @ 会刷屏
- **发文本、发文件**：图片走图片通道、其余走文件通道，各自的上限先拦一道并说人话
- **收入站的图片/文件**：落到 `<管家目录>/state/files/feishu/`，折成接缝要的 `LocalFile`
  （`path`/`name`/`mime`/`size`/`kind` 都填上），agent 直接读那个路径就行
- **`doctor` 自检**：凭据**真探一次活**（一次免费的 REST 调用，不用连长连接就能验），
  外加去重表放哪。被拒时只说事实（code / message）并摆出两种可能 —— 因为"被拒"不等于"凭据错"
- **没凭据也能装上**：这一行是**懒造**的（第一次真要用才构造官方通道）。所以"还没填
  app_id"是**正常状态**——插件照常装载，`doctor` 里如实报 ✗ 并指向探针，`butler run`
  时说一句人话；而不是整个插件装载失败（官方包在**构造时**就校验凭据）

## 它不做什么（如实）

- **不自己实现协议**。这不是偷懒，是取舍：抄一份协议层，飞书改协议时是我们先坏
- **超过上限的入站附件不落盘**（默认 30 MB，`maxFileMb` 可调）：落了盘才发现太大就删掉，
  宁可少一个附件，也不让 agent 去读一个 100 MB 的文件
- **单聊准入能收紧了**（第 59 轮补上；在那之前这一条写的是"还没做"）。`dmMode` 的四个取值
  原样透给官方（`open` / `allowlist` / `pair` / `disabled`，默认 `open`，和官方实现里的默认一致），
  `dmAllowlist` 填**发送者** id（`ou_…` / `user_id` / `union_id`）。在 `config.json` 那条通道的
  `config` 下加两行就行：

  ```json
  { "dmMode": "allowlist", "dmAllowlist": ["ou_先说句话的那个人"] }
  ```

  ⚠️ 别往里填应用 id（`cli_…`）：官方要的是**发送者**，填 `cli_` 等于谁也没放行 ——
  这种"看着配好了其实没配"最坑，所以 `start()` 会替你喊一声（但**不替你改**，照传）。
  `dmMode` 写错（比如 `allowList`）会在**装载时**就报错，不会悄悄按 `open` 放行 ——
  官方对不认识的取值是照 `open` 处理的，那种沉默更危险。
- **不做入站语音转写**。微信那条路是平台已经转好的文字；飞书要自己接 ASR，还没做
- **没有"正在输入"**。飞书没有这个概念，接缝上是默认的空实现
- **还没做卡片/按钮审批**。真要做审批，飞书这块比微信强得多（按钮能回传），值得专门做
- **真机还没验收过**。代码和 73 个离线用例都在，但"在真飞书里收发一条"还没跑过

## "我们没重写协议"这句话的证据

这个包运行时只 import 三样东西，没有 HTTP 客户端、没有 protobuf、没有 WebSocket：

```
@larksuite/channel                       ← 协议全在这儿
@butler/seam-channel                     ← 接缝
@deepseek-ai/{cordis,schemastery}        ← 插件与配置校验
```

## 怎么跑（真机冒烟，五分钟）

```bash
bash packages/channel-feishu/probe/run.sh        # 源码树里；装完之后用 CLI 给的那条完整命令
```

> 上面是**源码树里**的写法。探针现在跟着包一起发（`package.json` 的 `files` 里带着 `probe`），
> 所以**装完之后** CLI 的报错和引导页会给出一条完整命令：`node <包内路径>/probe/smoke.mjs --save`
> —— 不依赖 bash，也不依赖可执行位，两个平台一样。

没凭据它会走 **`registerApp` 扫码注册** —— 不需要开发者后台点那一串步骤，
也不需要公网 IP，手机飞书在手边就行。想先看要做什么而不联网：

```bash
bash packages/channel-feishu/probe/run.sh --dry  # 源码树里
```

加 `--save` 就不只是验一遍，而是**直接把凭据装好**：

```bash
bash packages/channel-feishu/probe/run.sh --save # 源码树里；装完之后用 CLI 给的那条完整命令
```

它把 `app_id` / `app_secret` 按 CLI 认的格式写进 `<管家目录>/state/secrets.json`
（**合并写、0600、原子写**，不碰你已有的 Telegram token），而且**不把凭据打印到终端**。

默认写的是 `~/.butler`。如果你当初是用 `--config` 把家安在别处（`butler init` 会打印
它写在哪），就加一句 `--home=<那个目录>`，别让凭据落在一个管家不看的地方：

> ⚠️ **验完先 `Ctrl-C` 掉探针，再 `butler run`**。同一个应用开两条长连接时，飞书会把事件
> 在两条之间**分流投递**（官方 README 讲 `onRawEvent` 时写明了这一点）—— 表现是
> "消息偶尔不回"，而两边看起来都正常。

```bash
bash packages/channel-feishu/probe/run.sh --save --home=/srv/butler  # 源码树里
```
之后：

```bash
butler init --im feishu    # 生成那份「收飞书」的配置（通道那一行换成这个包）
butler run                 # 凭据已经存过 → 它自动跳过问凭据那一步
```

探针**不 import 适配层**（只用官方包 + 一个只负责写凭据文件的 `probe/save.mjs`），
所以它是一把干净的尺子：它通了而管家不通，问题一定在适配层。通了就一次性证明五件事：
凭据、长连接、事件投递、权限点、回复。

## 测试

```bash
pnpm --filter @butler/channel-feishu test    # tsc + 60 个离线用例
```

其中 9 条是**探针的**（`test/probe.mjs`）：凭据落盘的形状、0600、合并写（不碰别人的 token）、
坏文件覆盖、不留临时文件，以及 `--dry` **不联网不落盘**。最后一条尤其重要 —— 探针是你打的
第一条命令，它崩了就是"第一印象崩了"。落盘形状这条还兼职**跨包契约**：写的那半在这儿钉着，
读的那半钉在 `packages/cli/test/secrets.mjs`，谁改形状另一边就会红。而"两半各自钉住"也还不
等于"合起来通"，所以另有一条**真跑一次**的集成测试（`packages/cli/test/probe-contract.mjs`）：
拿假凭据真跑一遍探针，再用 CLI 自己的读法读回来。

`test/types.mjs` 是**唯一用真 `@larksuite/channel`** 去跑 `normalize()` 的一份：拿 14 组原始事件
问官方"这种消息你渲染成什么"，再问我们这层"有没有弄丢"。它存在的理由是一个真发生过的 bug ——
见 `docs/CHANNEL-FEISHU.md` 第十一节第 18 轮。

`test/tarball.mjs` 盯的是**另一种安装形态**：真打个包、解开、从解开的副本里 `--dry` 跑一次探针，
并断言**提示里那条路径在这份副本里真的存在**。理由是上面那些"照着跑"的命令在源码树里当然通，
可装好之后（`install.sh` → `~/.butler/prefix`，没有 `packages/`）通不通，只有真打一次包才知道 ——
`files` 曾经漏过 `probe`，而 11 处文字都在承诺它（见第十一节第 14 轮）。

顺带一条用户能感觉到的性质：**凭据写盘在连长连接之前**。新应用权限还没配齐、第一次连不上时，
**凭据已经存好了** —— 修完权限直接 `butler run`，不用重扫。

离线测试的边界假在**"官方通道的接口"**上（`test/fake-lark.mjs`），不是假飞书服务器 ——
理由写在那个文件头：协议不是我们的代码，该证明的是我们这层翻译对不对
（重复投递拦住没有、回复走了原生引用还是普通发送、被引原文带上没有）。
真机那部分由上面的探针负责。

**端到端**不在这儿：这个包的测试到"适配层"为止（假大脑：一个数组）。真的把通道和内核拼起来
那四条在 `packages/cli/test/m1-feishu-e2e.mjs`（真通道 + 真内核 + 假大脑）；产品级"空凭据也
装得上"的回归在 `packages/cli/test/real-composition.mjs`。分层是故意的：**谁该为哪一段负责，
测试就放在哪一段**。

## 没验的

- 真机全流程：扫码注册、长连接、事件投递、权限点、群里的行为
- 话题群（`chatMode: 'topic'`）里 `threadId` 的**实际取值**（代码这一侧是确定的：官方从
  target 的 `threadId` 推出 `reply_in_thread`，我们按合同把它传下去并且钉了测试 ——
  没验的只是"真飞书的话题群到底给不给 `thread_id`"）
- 入站附件的**真机实测**（代码接好了：官方 `downloadResourceToFile` → `state/files/feishu/` →
  折成 `LocalFile` 交给大脑，离线用例在 `test/files.mjs` 与 `packages/cli/test/m1-feishu-e2e.mjs`；
  没验的是"真飞书的各种附件类型喂进来会怎样"）
- 长时间运行的稳定性（重连与心跳归官方包管，我们没压过）
