# @butler/channel-telegram

`ctx.channel` 的**第二个实现**。它同时是通道层抽象的一次验证：加一个 IM，
应该只多一个包 + 配置里换一行 `name`。

```jsonc
// ~/.butler/config.json 里那一行
{ "id": "channel", "name": "@butler/channel-telegram", "config": { "home": "…", "botToken": "123456:ABC-DEF…" } }
```

拿它跟微信那条路对比着看，最省事：

```bash
butler init --im telegram    # 配置里那一行就是 telegram
butler doctor                # 四个能力位照旧；通道自己的自检也会出现在里面
butler run                   # 贴模型 key → 上线
```

## 为什么它是"零依赖"

Bot API 是**纯 JSON over HTTPS**，需要用到的只有七个方法。所以这里就是 `fetch`
加一层错误翻译，`node:` 之外一个依赖都没有。

多一个依赖就多一份供应链风险 —— 而这一层碰的是用户的电脑。所以没拉库。

## 怎么收信的（两个循环，不是一个）

```
getUpdates 长轮询 ──归一化(纯函数)──> 队列 ──> 下载 worker ──> emitMessage
                                                                    ↑
                                                        到这里附件已经是本机路径
```

为什么必须分开：Telegram 取附件是**两次**请求（`getFile` 拿路径、再下载字节）。
在长轮询里干这件事，一个 20MB 的文件就足以让轮询超时、把消息漏掉。
seam 的注释里写着"`emitMessage` 不能阻塞收信循环"，这里就是那条规矩的实现。

## 三个"宁可这样，也不要那样"

| 场景 | 选择 | 为什么 |
| --- | --- | --- |
| `offset` 文件丢了/坏了 | **跳过积压**（问一次最新 update 的 id 然后从那儿开始） | 从 0 重放会让 Telegram 把最近 24 小时的消息再发一遍 —— 用户昨天说过的"清空下载文件夹"会被再执行一次。**宁可漏，不可重** |
| 附件超过上限（默认 20MB） | 不下载，在消息里说明一句 | 静默丢掉会让人以为管家没看见；说了，他就知道该换个方式发 |
| `stop()` 时长轮询还挂着 | 掐断请求，毫秒级返回 | 等它自己超时的话，`Ctrl-C` 之后要等 25 秒才退出，用户会以为卡死了 |

## 出错的时候用户会看到什么

Telegram 的错误描述是英文、而且带实现细节（`Conflict: terminated by other
getUpdates request`）。直接抛出去等于没抛，所以按错误码翻成人话：

| 码 | 用户看到的 |
| --- | --- |
| 401 | Telegram 说这个 token 不认 —— 复制的时候可能少了几位 |
| 409 | 同一个机器人有**另一个程序**正在收信，消息会随机分给两边，表现是"有时不回" |
| 429 | 发得太快了，Telegram 让我们等一下再发 |

同一个错**只大声说一次**，之后安静退避重试 —— 刷屏的日志没有信息量。

## 已知的粗糙处（说清楚，别当成没有）

1. **语音不转写。** 微信那边是服务端把语音转成文字给我们的；Telegram 没有
   这个能力。所以语音消息会以"只有附件、没有文字"的样子交上去，管家会说它
   听不懂 —— 这是实话，不是 bug。
2. ~~**`botToken` 得自己填一行配置。**~~ **已收掉**：`butler run` 现在会起引导页
   问你要那串 token（页面里 @BotFather 是能点的链接），存进 `~/.butler/state/secrets.json`
   （0600）。手写进 `config` 仍然可以，而且**优先级最高** —— 见
   [`packages/cli`](../cli) 的「凭据都在哪」那一节。
   （微信那条路是扫码：同样不用填任何东西，只是形式不同。）
   换一个机器人（或者在 @BotFather 那边 `/revoke` 过之后）：`butler run --again`。

**自检会真去验一次 token**：`butler doctor` 里那句「Telegram 登录态」不再是"配置里有一串
东西"，而是真问一句 `getMe`（免费、不要权限、5 秒上限）—— 连上了就把机器人名字报出来；
对面**明确拒了**（401/404，比如你在 @BotFather 那边 revoke 过）就当场判 ✗ 并给出
`butler run --again`。**连不上网不算故障**：那时候它说"这次没查"，不报红。
3. **引用是"两套同时在用"。** 见下面那一段 —— 这是这次做第二个通道**找出来的
   一个真问题**，不是这个包的锅。

## ★ 这次做第二个通道，找出来的一个真问题（**已修**）

微信的协议里**没有引用回复字段**，所以"我在回哪一句"只能把原话截 30 个字
顶在文本前面（`↩ 昨天那个 PPT`）。这事本身没问题 —— 问题是**这行前缀是内核
加的**（`packages/core/src/index.ts`），而不是通道加的。

而 Telegram **有**原生的引用回复字段。于是当时的 Telegram 用户体验是"同一句话
被引用了两次"：通道带原生引用（`reply_to_message_id`）**并且**内核还顶了一行 `↩`。

不疼，但它是"这个 seam 漏了一处"的证据：**"怎么表示引用"是通道的事**。

修法就是给 `SendOpts` 加了一个字段：

```ts
interface SendOpts {
  contextToken?: string
  quote?: string          // ← 这条消息在回哪句（原文；怎么显示是通道的事）
  maxChars?: number
  caption?: string
}
```

| 谁 | 拿到 `quote` 之后 |
| --- | --- |
| 内核 | 只说事实：`{ contextToken, quote: msg.text }`。**一个字都不拼** |
| `channel-wechat` | 顶一行 `↩ 原话`（协议没别的办法）—— 用户看到的东西和以前一模一样 |
| `channel-telegram`（本包） | 走原生引用回复，文本一个字不动 |
| 进度提示 / 附件配文 / 报错 | **不传 `quote`** → 不引用。以前它们会被内核一起顶上前缀，现在只有真正的答复才引用 |

顺带把内核里那份 `quoteLine`（微信形态的文案）删掉了 —— 它现在住在通道里。

**入站那半也修了**：引用现在走 `InboundMessage.quote`（见 `src/update.ts` 的
`quoteTextOf`），**不并进正文**。

- 微信那边挂在 `ref_msg` 上、本包挂在 `reply_to_message` 上 —— 形状不同，字段同一个；
- **只引用、没说话**也是内容（用户指着某句话）：照样交上去，不回"读不了"、也不静默丢；
- **文件也认 `quote`**：本包的 `sendFile` 会把附件挂成那条消息的原生引用回复
  （和文本一条规则）—— 微信的发文件没有这个能力，那边是如实忽略；
- 内核把引用作为**上下文**放进提示词（agent 才知道他在回哪句），但**路由只看正文**：
  引用里出现 `@某台设备` 不算在叫设备（那是他以前说过的话）；
- 顺带修掉一个真能踩到的问题：以前引用并进正文，`@设备` 出现在引用里就会让
  这条消息被送到那台设备上去执行。
